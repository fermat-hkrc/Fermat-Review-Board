## 漏洞概述

Snooze 通知列表的插入、清理和最早时间查询使用 `snoozeNotificationMutex_`，但 `CheckSnoozeTimer` 直接无锁执行 `snoozeDelayTimerList_.empty()` 并据此启动或销毁 timer。多个调用点在释放列表锁后才执行该检查。

## 根本原因

**位置**：`services/ans/src/snooze_delay_manager.cpp`

```cpp
void SnoozeDelayManager::CheckSnoozeTimer()
{
    if (snoozeDelayTimerList_.empty()) { // 未持有 snoozeNotificationMutex_
        DestroyTimer();
    } else {
        StartTimer();
    }
}
```

另一个线程可以在列表操作解锁与 `CheckSnoozeTimer` 读取之间改变容器状态，使检查和 timer 决策使用不同版本的数据。

## 影响

- 可能多启动一次 timer，或在列表仍有项目时错误销毁 timer。
- Snooze 通知可能延迟恢复或使用错误的触发时间。
- 无锁容器读取与修改构成数据竞争。

## 触发条件

timer 回调与应用创建、取消 snoozed notification 的服务任务重叠，并在一条路径释放列表锁后、执行空检查前修改列表。

## 修复建议

把列表状态检查和 timer 启停决策放进同一临界区，或在锁内计算不可变的下一触发时间并在锁外仅执行对应 timer 操作。

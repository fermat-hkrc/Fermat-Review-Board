## 漏洞概述

`AnsNotification::GetBundleImportance` 使用局部变量 `importanceTemp` 接收 IPC 输出。该变量声明时没有初始值，函数调用代理后也没有先检查返回码，而是立即将其参与枚举范围比较。

IPC 调用存在多种不产生有效输出的失败情况。服务端在无法为调用方生成 Bundle 信息时会直接返回 `ERR_ANS_INVALID_BUNDLE`，不会写入输出引用；远端对象失效、请求发送失败或回复解析失败同样不能保证输出参数已写入。客户端仍读取 `importanceTemp`，在未启用自动变量初始化的构建中构成 C++ 未定义行为。

该函数通过 `NotificationHelper::GetBundleImportance` 进入 `ans_innerkits`，不是测试代码。当前 `master` 提交 `c76a751c286e4e3fc614b4fccd57dfbfa13d2aa3` 仍存在该问题。本地可核对的 `OpenHarmony-v4.0-Release` 和 `OpenHarmony-v6.0-Release` 均包含相同模式；尚未确认已修复发行版。

## 根本原因

### 客户端在检查 IPC 返回值之前消费输出

**位置**: `frameworks/core/src/ans_notification.cpp:713`

```cpp
ErrCode AnsNotification::GetBundleImportance(NotificationSlot::NotificationLevel &importance)
{
    sptr<IAnsManager> proxy = GetAnsManagerProxy();
    if (!proxy) {
        ANS_LOGE("GetAnsManagerProxy fail.");
        return ERR_ANS_SERVICE_NOT_CONNECTED;
    }
    int32_t importanceTemp;
    ErrCode ret = proxy->GetBundleImportance(importanceTemp);
    if ((NotificationSlot::LEVEL_NONE <= importanceTemp) &&
        (importanceTemp <= NotificationSlot::LEVEL_HIGH)) {
        importance = static_cast<NotificationSlot::NotificationLevel>(importanceTemp);
    } else {
        importance = NotificationSlot::LEVEL_UNDEFINED;
    }
    return ret;
}
```

正确顺序应是先判断 `ret`。当前范围比较无条件执行，因此代理是否成功写入输出与客户端是否读取输出之间没有约束。

### 服务端失败分支不写输出参数

**位置**: `services/ans/src/advanced_notification_service.cpp:1525`

```cpp
ErrCode AdvancedNotificationService::GetBundleImportance(int32_t &importance)
{
    sptr<NotificationBundleOption> bundleOption = GenerateBundleOption();
    if (bundleOption == nullptr) {
        ANS_LOGD("GenerateBundleOption failed.");
        return ERR_ANS_INVALID_BUNDLE;
    }

    ErrCode result = ERR_OK;
    auto submitResult = notificationSvrQueue_.SyncSubmit(
        std::bind([&]() {
            result = NotificationPreferences::GetInstance()->GetImportance(bundleOption, importance);
        }));
    ANS_COND_DO_ERR(submitResult != ERR_OK, return submitResult, "Get bundle importance.");
    return result;
}
```

`GenerateBundleOption` 失败时不会触及 `importance`。队列提交失败时，也可能在任务没有执行的情况下直接返回 `submitResult`。IDL 将该参数声明为 `[out] int`，因此调用方不应被要求预先提供有效输入。

调用链为 `NotificationHelper::GetBundleImportance` → `AnsNotification::GetBundleImportance` → 生成的 `IAnsManager` 代理 → `AdvancedNotificationService::GetBundleImportance`。`frameworks/ans/BUILD.gn` 将客户端实现编译进 `ans_innerkits`，同时从 `IAnsManager.idl` 生成代理和存根。

## 影响

- IPC 失败时，客户端仍会读取一个没有成功结果保证的局部整数。
- 若不确定值恰好位于有效枚举范围，调用方可能同时收到错误码和一个看似有效但错误的重要性级别；超出范围时则得到 `LEVEL_UNDEFINED`。
- 在未启用局部变量自动初始化的构建中，该读取属于 C++ 未定义行为，并可能受到栈上残留值影响。
- OpenHarmony 标准 OHOS C++ target 默认将普通局部变量置零，且 `ans_innerkits` 没有关闭该保护。在标准配置下风险通常退化为失败时临时得到 `LEVEL_NONE`，但返回结果仍与 IPC 成功状态脱节。

能够正确检查返回码的上层不会使用失败输出。当前没有证据支持跨进程内存泄露、稳定崩溃、权限绕过或调用方可控制 `importanceTemp` 内容的结论。

## 触发条件

1. 调用方通过 `NotificationHelper::GetBundleImportance` 发起查询，且客户端代理对象已经建立。
2. IPC 请求返回错误，例如远端对象失效、回复读取失败，或服务端 `GenerateBundleOption`、通知服务队列提交失败。
3. 失败路径没有提供有效的 `importanceTemp`。
4. 客户端在检查并返回错误码之前执行范围比较。

代理对象一开始就不存在时，函数会在声明 `importanceTemp` 之前返回，不属于本报告的触发路径。

## 修复建议

初始化临时输出，并在任何枚举转换前检查代理返回值。失败时应把公开输出设置为明确的 `LEVEL_UNDEFINED`：

```cpp
int32_t importanceTemp = static_cast<int32_t>(NotificationSlot::LEVEL_UNDEFINED);
ErrCode ret = proxy->GetBundleImportance(importanceTemp);
if (ret != ERR_OK) {
    importance = NotificationSlot::LEVEL_UNDEFINED;
    return ret;
}
if (NotificationSlot::LEVEL_NONE <= importanceTemp &&
    importanceTemp <= NotificationSlot::LEVEL_HIGH) {
    importance = static_cast<NotificationSlot::NotificationLevel>(importanceTemp);
} else {
    importance = NotificationSlot::LEVEL_UNDEFINED;
}
return ERR_OK;
```

服务端也可在函数入口为 `importance` 设置安全默认值，使所有失败返回遵循一致的输出约定；但客户端仍必须以 IPC 返回码为准，不能依赖失败回复一定包含输出字段。

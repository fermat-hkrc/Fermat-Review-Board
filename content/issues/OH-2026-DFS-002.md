## 漏洞概述

`CloudFileDaemon` 处理 Cloud Media FUSE 读取请求时，会按请求长度分配一个未清零的回复缓冲区。云端读取完成后，`ReadFileToBuf` 从本地缓存文件读取数据，并返回实际读取字节数；`FixData` 也只把这些实际字节复制到回复缓冲区。但是，`WaitAndFixData` 仍按每个分片的请求长度累加已完成字节数，并把该长度传给 `fuse_reply_buf`。

当本地缓存文件发生 EOF 短读、部分读取后出错，或实际长度与元数据不一致时，回复长度可能大于已写入长度。调用方随后可能收到回复缓冲区中未被本次读取覆盖的尾部数据。这些字节来自 `cloudfiledaemon` 的未初始化堆内存，可能造成跨进程信息泄露。

该路径要求调用方已经具备对应 Cloud Media 文件的读取权限，并且本地缓存读取实际返回少于请求长度。当前没有证据表明调用方能够稳定控制泄露内容，也未确认可绕过原有文件访问权限。

受影响版本仅确认提交 `38dc2f94b310e6406792999cd7b0c308be74a6ef`。仓库中可核对的公开 tag 均早于构成当前短读路径的相关变更，因此尚未确认首个受影响发行版或已修复发行版。

## 根本原因

### 回复缓冲区未初始化

**位置**: `services/cloudfiledaemon/src/fuse_manager/fuse_manager.cpp:1881`

`CloudRead` 按 FUSE 请求长度分配回复缓冲区，但没有对其进行值初始化或清零：

```cpp
buf.reset(new char[size], [](char *ptr) { delete[] ptr; });
if (!buf) {
    fuse_reply_err(req, ENOMEM);
    CLOUD_FILE_FAULT_REPORT(CloudFileFaultInfo{PHOTOS_BUNDLE_NAME, FaultOperation::READ,
        FaultType::FILE, ENOMEM, "buffer is null"});
    return;
}
```

标准设备路径随后把这个缓冲区交给 `WaitAndFixData`。`SUPPORT_WATCH_LITE` 路径也使用未清零的 `new (std::nothrow) char[size]`，并进入同一组合与回复函数。

### 本地缓存读取明确允许短读

**位置**: `services/cloudfiledaemon/src/fuse_manager/fuse_manager.cpp:1397`

`ReadFileToBuf` 循环调用 `pread`。遇到 EOF 或读取错误时，它会停止读取，并返回此前实际写入缓冲区的 `readLen`：

```cpp
ssize_t n;
size_t readLen = 0;
while (readLen < size) {
    n = pread(fd, buf + readLen, size - readLen, off + readLen);
    if (n > 0) {
        readLen += static_cast<size_t>(n);
    } else if (n == 0) {
        break;
    } else {
        LOGE("pread failed, return: %{public}zd", n);
        break;
    }
}

close(fd);
int64_t result = static_cast<int64_t>(readLen);
return result;
```

`ExecuteCloudRead` 在 `CloudAssetReadSession::PRead` 成功后调用该函数，并把实际读取长度保存到 `readResult`：

```cpp
*readArgs->readResult = readSession->PRead(readArgs->offset, readArgs->size, *readArgs->ckError, readArgs->appId);
if (*readArgs->readResult == 0) {
    *readArgs->readResult = ReadFileToBuf(data->cachePath, readArgs->buf.get(), readArgs->size, readArgs->offset);
} else {
    LOGE("read cloud file failed, read result: %{public}" PRId64 ", error: %{public}d",
        *readArgs->readResult, *readArgs->ckError);
}
```

因此，`readResult` 可以是介于零和分片请求长度之间的非负值。`ReadFileToBuf` 在第一次 `pread` 就失败时也会返回零，而不是错误码。

### 复制长度与回复长度使用不同口径

**位置**: `services/cloudfiledaemon/src/fuse_manager/fuse_manager.cpp:1609`

`FixData` 使用 `readResult` 限制复制长度，因此只初始化实际读取到的字节：

```cpp
int32_t copyRet = memcpy_s(buf.get() + sizeDone, min(size - sizeDone, static_cast<size_t>(*readArgs->readResult)),
                           readArgs->buf.get(), min(size - sizeDone, static_cast<size_t>(*readArgs->readResult)));
if (copyRet != 0) {
    fuse_reply_err(req, ENETUNREACH);
    string msg = "Parcel data copy failed, err=" + to_string(copyRet);
    CLOUD_FILE_FAULT_REPORT(CloudFileFaultInfo{PHOTOS_BUNDLE_NAME, FaultOperation::READ,
        FaultType::FILE, copyRet, msg});
    return false;
}
```

**位置**: `services/cloudfiledaemon/src/fuse_manager/fuse_manager.cpp:1646`

`WaitAndFixData` 在复制后没有累加实际复制长度，而是累加分片请求长度 `it->size`，最后按该值回复：

```cpp
for (auto &it : readArgsList) {
    if (!it) {
        continue;
    }
    if (!WaitData(req, cInode, it)) {
        return;
    }
    ReadSize sizes;
    sizes.size = size;
    sizes.sizeDone = sizeDone;
    if (!FixData(req, buf, sizes, it, prepareTraceId)) {
        return;
    }
    sizeDone += it->size;
}
fuse_reply_buf(req, buf.get(), min(size, sizeDone));
```

假设一次读取请求需要 `N` 个字节，而本地缓存只返回 `R` 个字节且 `R < N`。`FixData` 只写入前 `R` 个字节，但 `sizeDone` 仍按 `N` 增加，`fuse_reply_buf` 随后回复 `N` 个字节。区间 `[R, N)` 没有被本次读取写入。

跨越分片边界时问题同样存在。若前一分片短读，后一分片仍从前一分片的请求长度位置开始复制，中间会留下未初始化空洞；最终回复长度仍由请求长度之和决定。

### 该路径进入生产构建和 FUSE read 回调

`FuseManager::StartFuse` 为 Cloud Media 挂载创建 `cloudMediaFuseOps` 会话。该操作表在标准设备上把 `.read` 指向 `CloudRead`，在 `SUPPORT_WATCH_LITE` 构建中指向 `CloudReadForWatch`。两条路径最终都会调用 `WaitAndFixData`。

`services/cloudfiledaemon/BUILD.gn` 把 `src/fuse_manager/fuse_manager.cpp` 编译进 `cloudfiledaemon`。组件根 `BUILD.gn` 的 `services_target` 依赖该目标，`bundle.json` 再把 `services_target` 列入 `service_group`，因此该实现属于产品服务构建，不是测试或示例代码。

历史上，未清零回复缓冲区、`FixData` 以及按请求长度累加的 `WaitAndFixData` 由提交 `4607a266` 在 2024-06-29 一并引入。提交 `8b6ef05f` 在 2026-01-24 增加了当前 `ReadFileToBuf` 缓存读取流程，使实际短读长度明确进入原有回复组合逻辑。复核基线仍保留这一行为。

## 影响

- FUSE 读取进程可能收到 `cloudfiledaemon` 回复缓冲区中未被本次文件读取覆盖的堆内存字节。
- 泄露发生在服务进程与读取进程之间，可能暴露同一服务进程先前处理的数据或其他堆内容。
- 即使未初始化区域恰好为零，按请求长度回复短读仍会破坏正常的 EOF 和部分读取语义。
- 本地文件描述符快速路径 `CloudReadOnLocalFile` 使用实际 `pread` 返回值作为回复长度，不受本报告所述长度口径错误影响。

本次只完成了指定源码、调用链、构建入口和提交历史复核，没有在设备上制造缓存短读，也没有观察到实际泄露字节。因此，当前不声称泄露内容可控、可稳定包含敏感数据，或能够进一步导致权限提升和代码执行。

## 触发条件

1. Cloud Media FUSE 挂载已经由 `cloudfiledaemon` 建立，调用进程具备目标云文件的读取权限。
2. 读取进入云端或缓存组合路径，而不是持有本地文件描述符的 `CloudReadOnLocalFile` 快速路径。
3. `CloudAssetReadSession::PRead` 成功后，本地缓存文件在请求区间发生 EOF 短读、部分读取后出错，或实际缓存长度小于元数据所表示的长度。
4. `ReadFileToBuf` 返回小于分片请求长度的非负值，`FixData` 只复制实际字节。
5. `WaitAndFixData` 按请求长度计算 `sizeDone`，并通过 `fuse_reply_buf` 返回包含未写入尾部或空洞的缓冲区。

源码确认上述条件成立时会回复未完全初始化的范围。非特权应用能否在受支持的产品配置中稳定制造所需的缓存长度不一致，尚未通过动态测试确认。

## 修复建议

`FixData` 应返回本次实际复制的字节数。`WaitAndFixData` 必须按该实际值更新 `sizeDone`，并最终只把连续、已初始化的 `[0, sizeDone)` 区间传给 `fuse_reply_buf`。

如果某个分片返回值小于该分片需要提供的长度，应将其视为短读并停止后续分片组合，直接回复此前连续读取到的字节。不能继续按后续分片的请求偏移写入，否则会在回复中保留空洞。

`ReadFileToBuf` 还应区分 EOF 和读取错误。若尚未读取任何字节就发生 `pread` 错误，应向上返回错误；若已经读取部分数据，可以按 POSIX 部分读取语义返回实际字节数，但回复层仍只能返回这些字节。

同时建议对回复缓冲区使用值初始化或显式清零，作为防止未来长度计算错误泄露堆内存的附加保护。清零不能替代正确的实际长度统计，否则仍会向调用方返回错误数量的零填充数据。

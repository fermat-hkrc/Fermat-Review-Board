## 漏洞概述

Bun 的 Rust 代码中存在多处不安全的 `Send`/`Sync` trait 实现，泛型类型参数缺少必要的 trait bound，允许安全代码构造出不应该跨线程传递的值并发送到其他线程，违反 Rust 的内存安全保证。

**严重程度**: HIGH  
**置信度**: HIGH  
**影响范围**: 3 个核心类型

## 受影响的类型

### 1. `JsCell<T>` — 无条件的 `Send` + `Sync`，且 `get(&self) -> &T` 是安全函数

**文件**: [`src/jsc/JSCell.rs#L117-L142`](https://github.com/oven-sh/bun/blob/2148214d40fc9f844f61ae5f8575d6d94a9d038c/src/jsc/JSCell.rs#L117-L142)

```rust
#[repr(transparent)]
pub struct JsCell<T>(core::cell::UnsafeCell<T>);

unsafe impl<T> Sync for JsCell<T> {}   // ← 缺少 T: Sync bound
unsafe impl<T> Send for JsCell<T> {}   // ← 缺少 T: Send bound

impl<T> JsCell<T> {
    pub fn get(&self) -> &T {           // ← 安全函数！
        unsafe { &*self.0.get() }
    }
}
```

**问题**: 结合 `Sync`，`&'static JsCell<T>` 可以跨线程发送。安全的 `get()` 函数在接收线程返回 `&T`。如果 `T` 是 `!Sync` 类型（如 `Cell<U>`, `Rc<U>`, `RefCell<U>`），这会导致 UB。

**影响**: 单 JS 线程不变式是运行时契约，不由类型签名强制。任何后续代码写出 `JsCell<Rc<Foo>>` 都会在**无需 `unsafe`** 的调用点破坏内存安全。

### 2. `ConcurrentPromiseTask<'_, C>` — `Send` 缺少 `C: Send`

**文件**: [`src/jsc/ConcurrentPromiseTask.rs#L31-L55`](https://github.com/oven-sh/bun/blob/2148214d40fc9f844f61ae5f8575d6d94a9d038c/src/jsc/ConcurrentPromiseTask.rs#L31-L55)

```rust
pub struct ConcurrentPromiseTask<'a, Context: ConcurrentPromiseTaskContext> {
    pub ctx: Box<Context>,              // ← 拥有的堆值
}

unsafe impl<C: ConcurrentPromiseTaskContext> Send for ConcurrentPromiseTask<'_, C> {}
//                                          ^^^^ 缺少 C: Send
```

**问题**: `ctx: Box<Context>` 是按值拥有的。任务被发送到工作池并在工作线程解引用：

```rust
pub unsafe fn run_from_thread_pool(task: *mut WorkPoolTask) {
    let this = unsafe { Self::from_task_ptr(task) };
    unsafe { (*this).ctx.run() };       // ← 在工作线程调用 Context::run
    Self::on_finish(this);
}
```

如果 `Context` 包含 `!Send` 字段（`Rc<…>`, `*mut U`, `MutexGuard<…>`），在不同 OS 线程运行其 `run()` 是 UB。trait `ConcurrentPromiseTaskContext` 本身不强制 `Send` bound。

**当前状态**: 现有的 4 个实现者（`CopyFile`, `TransformTask`, `WalkTask`, `PipelineTask`）恰好是 `Send` 的，但这依赖作者纪律，不是类型系统强制。

### 3. `WorkTask<C>` — 通过裸指针的相同模式

**文件**: [`src/jsc/WorkTask.rs#L36-L58`](https://github.com/oven-sh/bun/blob/2148214d40fc9f844f61ae5f8575d6d94a9d038c/src/jsc/WorkTask.rs#L36-L58)

```rust
pub struct WorkTask<Context: WorkTaskContext> {
    pub ctx: *mut Context,
}

unsafe impl<C: WorkTaskContext> Send for WorkTask<C> {}
```

**问题**: `ctx` 是裸指针，解引用已经是 `unsafe` 的，每个调用点的契约可以记录 bound。但由于使用指针的唯一合法方式是为 `Context::run` 解引用，要求 `C: Send` 会将义务转移到（单个）构造点而非每个调用点。

## 预期行为

每个泛型 `Send`/`Sync` impl 应要求类型参数上的相应 bound：

```rust
// JSCell.rs
unsafe impl<T: Sync> Sync for JsCell<T> {}
unsafe impl<T: Send> Send for JsCell<T> {}

// ConcurrentPromiseTask.rs
unsafe impl<C: ConcurrentPromiseTaskContext + Send> Send for ConcurrentPromiseTask<'_, C> {}

// WorkTask.rs
unsafe impl<C: WorkTaskContext + Send> Send for WorkTask<C> {}
```

或者 trait bound 本身应要求 `Send`：

```rust
pub trait ConcurrentPromiseTaskContext: Sized + Send { … }
pub trait WorkTaskContext:              Sized + Send { … }
```

这对当前代码零成本（每个实现者已经是 `Send`），并且**使未来的回归成为编译错误而非 heisenbug**。

## PoC 示例

```rust
// 假设的 PoC — 今天不会编译错误，但是 UB：
struct Boom { rc: std::rc::Rc<u32> }    // !Send + !Sync

impl ConcurrentPromiseTaskContext for Boom {
    const TASK_TAG: TaskTag = /* … */;
    fn run(&mut self) {
        // 在工作线程运行 — Rc<u32> 的非原子引用计数
        let _ = self.rc.clone();
    }
    fn then(&mut self, _: &mut JSPromise) -> Result<(), JsTerminated> { Ok(()) }
}

// 在 JS 线程的其他地方
let task = ConcurrentPromiseTask::create_on_js_thread(
    global, 
    Box::new(Boom { rc: Rc::new(1) })
);
// task 根据 unsafe impl 是 Send → 交给线程池 → UB
```

同样的模式适用于 `JsCell<Rc<U>>`：在非 JS 线程单次 `vm.field.get()` 就是 UB，且调用点无需 `unsafe`。

## 修复建议

1. **立即修复**: 为所有泛型 `Send`/`Sync` impl 添加必要的 trait bounds
2. **长期方案**: 在 trait 定义中要求 `Send`/`Sync`，使违规成为编译错误
3. **测试**: 添加编译失败测试确保 `!Send` 类型不能用于这些泛型

## 附加信息

- 通过静态分析发现（级别：`Error`）
- 仅提交缺少 bound 是真正 soundness gap 的情况
- 例如 `RacyCell<T>: Sync`（`util.rs:2323`）属于同一类别，但其公共读写 API 是 `unsafe fn`，义务正确转移给调用者 — **未提交该问题**
- 分析报告了许多其他类似模式的位置（`AtomicCell<T>`, `BSSList`, `ThreadCell<T>`, `Channel<T,B>` 等）；每个都通过 `unsafe fn` 或其 trait bounds（`T: Atom`, `T: Send`）在实践中已经隐含所需属性来保护危险部分。上述三个是**公共、安全** API 成为泄漏点的情况。

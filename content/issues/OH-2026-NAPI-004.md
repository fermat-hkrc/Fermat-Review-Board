## 问题概述

`ArkIdleMonitor::IntervalMonitor()` 在 `timerMutex_` 保护下读写 `numberOfLowIdleNotifyCycles_` 和 `numberOfHighIdleTimeRatio_`。`NotifyChangeBackgroundState()` 调用 `ClearIdleStats()` 时却没有持有这把锁，而且清理发生在停止 FFRT 定时任务之前。

因此，后台状态切换线程可以把两个普通 `uint32_t` 计数器清零，同时 FFRT 定时回调正在增加或读取它们。两个问题点分别对应两个共享计数器，合并为同一个同步缺陷。

## 源码证据

### 定时回调在 `timerMutex_` 下访问计数器

**位置**: `native_engine/impl/ark/ark_idle_monitor.cpp:194`

```cpp
void ArkIdleMonitor::IntervalMonitor()
{
    if (!timerMutex_.try_lock()) {
        return;
    }
    if (GetIdleNotifyCount() <= LOW_IDLE_NOTIFY_THRESHOLD) {
        numberOfLowIdleNotifyCycles_++;
    } else {
        numberOfLowIdleNotifyCycles_ = 0U;
    }
    // ...
    idleTimeRatio >= IDLE_RATIO ? numberOfHighIdleTimeRatio_++ : (numberOfHighIdleTimeRatio_ = 0U);
    // ...
    timerMutex_.unlock();
}
```

### 清理函数没有取得 `timerMutex_`

**位置**: `native_engine/impl/ark/ark_idle_monitor.cpp:272`

```cpp
void ArkIdleMonitor::ClearIdleStats()
{
    ResetIdleNotifyCount();
    numberOfLowIdleNotifyCycles_ = 0U;
    numberOfHighIdleTimeRatio_ = 0U;
    std::lock_guard<std::mutex> lock(envVectorMutex_);
    // ...
}
```

`envVectorMutex_` 在两个计数器被写入之后才取得，并且 `IntervalMonitor()` 访问计数器时也不以该锁作为同步条件，所以它不能保护这两个字段。

### 状态切换先清理，再停止定时任务

**位置**: `native_engine/impl/ark/ark_idle_monitor.cpp:446`

```cpp
void ArkIdleMonitor::NotifyChangeBackgroundState(bool inBackground)
{
    // ...
    ClearIdleStats();
#if defined(ENABLE_FFRT)
    if (started_ && inBackground) {
        StopIdleMonitorTimerTask();
        // ...
    }
#endif
}
```

OHOS 标准系统构建在 `BUILD.gn` 中启用 `ENABLE_FFRT` 和 `ENABLE_EVENT_HANDLER`。`PostMonitorTask()` 的回调由 FFRT 执行，因此它可以与状态切换调用并发运行。

## 影响与限制

- 两个普通整数存在未同步读写，按 C++ 内存模型属于数据竞争。
- 直接可见的影响是 IdleMonitor 连续周期统计丢失或状态不一致，可能提前、延后或跳过 idle GC 判断。
- 当前没有证据表明该竞态可以造成可控内存破坏或跨权限影响，因此等级定为 LOW。
- 本次只做了源码和构建条件复核，没有使用 ThreadSanitizer 或时序测试动态复现。

## 修复建议

为两个计数器建立单一同步规则。可以把清理逻辑拆成“调用方已持有 `timerMutex_`”的内部函数，并让外部清理入口先取得该锁；`IntervalMonitor()` 在现有锁作用域内调用内部函数，避免重复加锁。

状态切换路径还应先停止定时任务，再清理统计值。需要保持 `timerMutex_` 与 `envVectorMutex_` 的固定加锁顺序，避免引入锁顺序反转。

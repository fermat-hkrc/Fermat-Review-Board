## 漏洞概述

Notification Manager 的 CJ FFI 在把 `std::vector` 转换为 C 数组时，以输入容器长度分配未清零内存。转换循环允许跳过空对象或转换失败元素，但返回结构中的 `size` 仍使用原始容器长度，而不是实际成功写入的 `count`。

本报告合并两个同根因函数：`NotificationManagerImplV2::GetSlots` 返回内嵌结构数组，`NotificationManagerImplV2::GetActiveNotifications` 返回指针数组。只要循环跳过元素，调用方按照公开的 `size` 遍历时就会进入没有写入的尾部范围。前者会读取未初始化结构字段，后者可能把未初始化字节解释为指针并解引用或释放。

两个函数分别由 `FfiOHOSNotificationManagerGetSlots` 和 `FfiOHOSNotificationManagerGetActiveNotifications` 直接导出，并编译进 `cj_notification_manager_ffi` 产品共享库。当前 `master` 提交 `c76a751c286e4e3fc614b4fccd57dfbfa13d2aa3` 仍存在该问题。本地可核对的 `OpenHarmony-v6.0-Release` 标签已包含两个 V2 实现；尚未确认已修复发行版。

## 根本原因

### GetSlots 忽略实际转换数量

**位置**: `frameworks/cj/ffi/src/notification_manager_impl.cpp:123`

```cpp
CNotificationSlotV2* head = reinterpret_cast<CNotificationSlotV2 *>(
    malloc(sizeof(CNotificationSlotV2) * slots.size()));
if (head == nullptr) {
    return notificationSlots;
}
int32_t count = 0;
for (auto vec : slots) {
    if (!vec) {
        continue;
    }
    if (!SetNotificationSlotV2(*vec, head[count])) {
        continue;
    }
    count++;
}
notificationSlots.size = static_cast<int64_t>(slots.size());
notificationSlots.head = head;
```

`malloc` 不会清零数组。空 `sptr<NotificationSlot>` 和 `SetNotificationSlotV2` 失败都不会增加 `count`，后续成功元素会向前紧凑写入。若原始长度为 `N`、成功转换数为 `M`，函数却返回 `size = N`，因此 `[M, N)` 从未被有效写入。

`SetNotificationSlotV2` 在无法映射 Slot 类型或等级，以及振动数组分配失败时会返回 `false`，所以转换失败分支具有实际实现，不是恒假条件。

### GetActiveNotifications 对空元素和转换失败处理不一致

**位置**: `frameworks/cj/ffi/src/notification_manager_impl.cpp:177`

```cpp
CNotificationRequestV2** head = reinterpret_cast<CNotificationRequestV2 **>(
    malloc(sizeof(CNotificationRequestV2*) * requests.size()));
// ...
notificationRequests.size = static_cast<int64_t>(requests.size());
int32_t count = 0;
for (auto vec : requests) {
    if (!vec) {
        continue;
    }
    head[count] = reinterpret_cast<CNotificationRequestV2 *>(malloc(sizeof(CNotificationRequestV2)));
    if (head[count] == nullptr) {
        // 释放后把 head 设为 nullptr，但保留原 size。
        head = nullptr;
        break;
    }
    if (!SetNotificationRequestV2(vec.GetRefPtr(), *(head[count++]))) {
        continue;
    }
}
notificationRequests.head = head;
```

空请求不会增加 `count`，会在未清零的指针数组尾部留下空洞，但 `size` 已固定为 `requests.size()`。单个元素分配失败时，函数释放整个数组并返回 `head == nullptr`、`size > 0` 的不一致结果。

转换失败还存在另一处计数错误：`count++` 在 `SetNotificationRequestV2` 返回前已经执行。失败对象会作为数组中的有效项计数并返回，但其中可能只完成了部分字段初始化，也没有统一释放此前分配的嵌套资源。

两个 FFI 导出函数不再校正返回长度。`frameworks/cj/ffi/BUILD.gn` 将管理器、转换函数和导出层编译进同一个共享库，`bundle.json` 将该库作为组件 inner kit 发布。

## 影响

- `GetSlots` 的调用方可能从未写入的堆区读取整数、布尔值和指针字段，导致错误数据、残留堆内容暴露或在清理字符串和振动数组时访问无效地址。
- `GetActiveNotifications` 的调用方可能把未初始化的数组项当作 `CNotificationRequestV2*` 解引用或释放，造成进程崩溃；转换失败项也可能包含部分初始化的嵌套指针。
- `malloc` 内存不受局部变量自动零初始化保护，因此标准构建仍存在该长度与初始化范围不一致的问题。
- 问题发生在 CJ 调用进程内。当前没有证据表明未初始化内容可稳定控制，或能跨越原有通知读取权限。

本次没有执行设备端故障注入，也未确认服务在正常状态下是否会返回空 `sptr`。当前证据支持内存不安全的返回契约，但不声称稳定的信息泄露、代码执行或权限提升。

## 触发条件

`GetSlots` 路径需要满足以下任一条件：

1. 服务返回的槽位数组包含空对象；或者
2. 某个槽位使用当前 CJ 转换器不能映射的类型或等级；或者
3. 转换振动数组时发生内存分配失败。

`GetActiveNotifications` 路径需要服务返回空请求对象，或在转换通知请求、内容、图片等字段时失败。随后 CJ 调用方按照返回的原始 `size` 遍历数组，便会接触未写入或部分初始化的元素。

普通业务输入能否稳定制造空服务对象尚未确认。版本演进产生的新枚举值以及资源不足会使转换失败分支成为可达条件。

## 修复建议

两个函数都应把返回长度设置为实际成功转换的 `count`，并且只在元素完全转换成功后递增计数。输出数组可使用 `calloc` 或显式清零作为附加保护，但清零不能替代正确的长度统计。

`GetActiveNotifications` 应先在临时所有者中分配并完整转换单个请求，成功后再写入 `head[count]` 并增加 `count`。转换失败时必须释放该对象已经分配的字符串、内容和图片等嵌套资源。整体分配失败时应返回 `{ nullptr, 0 }` 并设置明确错误码。

```cpp
int64_t count = 0;
for (const auto& item : requests) {
    if (item == nullptr) {
        continue;
    }
    auto converted = AllocateAndConvertRequest(item);
    if (converted == nullptr) {
        continue;
    }
    head[count++] = converted.release();
}
notificationRequests.head = head;
notificationRequests.size = count;
```

`GetSlots` 应采用相同的“成功后计数”规则，并确保失败转换留下的临时资源得到释放。

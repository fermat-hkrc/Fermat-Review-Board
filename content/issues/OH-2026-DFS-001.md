## 复核结论

当前源码复核提交 `f40331de9b64f465ca1c33b88c1165e4124f6510` 中，不存在可控 `cloudId` 写入生产 dentry 的调用链。可见的对外入口要求 system app 和 `ohos.permission.CLOUDFILE_SYNC`，其默认 `DataSyncManager::BatchDentryFileInsert` 实现不写入 dentry；其他生产来源使用系统媒体数据库或内部生成的 ID。因此报告所需的“不可信路径片段 → dentry → rename/unlink”数据流不成立，本项标记为误报，不提交上游 Issue。

## 漏洞概述

Cloud Disk 将 `cloudId` 作为云端记录标识使用，但在把该值写入 dentry、从 dentry 恢复以及转换为本地文件路径的过程中，没有保证它是单一文件名组件。包含 `/` 和 `..` 路径片段的 `cloudId` 会被直接拼接到数据目录或缓存目录之后，并在 `cloudfiledaemon` 中到达 `rename()` 和 `unlink()`。

因此，在恶意 `cloudId` 已进入 Cloud Disk dentry 且满足相应文件操作条件时，路径解析可以逃出预期的 bundle/bucket 目录。可造成的结果包括删除守护进程有权访问的其他文件，或把缓存文件移动到预期目录之外的尚不存在位置。最终范围仍受 `cloudfiledaemon` 的 DAC 和 SELinux 权限限制。

当前仓库能够确认受影响的精确基线为 `38dc2f94b310e6406792999cd7b0c308be74a6ef`。公开标签快照中，`OpenHarmony-v6.0-Beta1` 和 `OpenHarmony-v6.0-Release` 仍包含所述 `rename()` 与常规 `unlink()` 路径；未对所有产品分支和设备配置建立包含关系，因此不据此推断完整发行范围。

## 根本原因

### cloudId 在可见入口处未进行路径语义校验

`CloudSyncManagerImpl::BatchDentryFileInsert()` 只限制批量条目数量，随后把每项转换为 IPC 对象。`CloudSyncService::BatchDentryFileInsert()` 再把 `obj.cloudId` 原样复制到 `DentryFileInfo` 并交给动态加载的 `DataSyncManager`：

```cpp
if (fileInfo.size() > MAX_DENTRY_FILE_SIZE) {
    return E_INVAL_ARG;
}

DentryFileInfo tmpFileInfo{
    obj.cloudId, obj.size, obj.modifiedTime, obj.path,
    obj.fileName, obj.fileType
};
```

这条 IPC 入口并非对普通应用开放。服务端要求调用方同时是 system app，并持有 `ohos.permission.CLOUDFILE_SYNC`。此外，实际 `DataSyncManager` 插件实现不在本仓库中；仓库内默认基类实现不会持久化这些条目。因此，从该 IPC 输入到 dentry 写入的部署时调用关系，以及云服务提供方能否直接控制 `cloudId`，仍取决于实际加载的插件，尚未确认。

无论 dentry 的上游来源为何，`UpdateDentry()` 都只依靠固定缓冲区大小约束复制长度，没有拒绝路径分隔符或遍历片段：

```cpp
(void)memset_s(de->recordId, CLOUD_RECORD_ID_LEN, 0, CLOUD_RECORD_ID_LEN);
ret = memcpy_s(de->recordId, CLOUD_RECORD_ID_LEN,
    base.cloudId.c_str(), base.cloudId.length());
```

`CloudDiskMetaFile::DoLookup()` 随后把 `recordId` 恢复为 `base.cloudId`，同样没有进行路径校验。

### 路径构造把标识符直接当作路径后缀

`CloudFileUtils::GetLocalFilePath()` 和 `GetLocalDKCachePath()` 均直接在可信基础目录和 bucket 编号之后追加 `cloudId`：

```cpp
string CloudFileUtils::GetLocalDKCachePath(string cloudId,
    string bundleName, int32_t userId)
{
    // baseDir 省略
    uint32_t bucketId = GetBucketId(cloudId);
    return baseDir + to_string(bucketId) + "/" + cloudId;
}

string CloudFileUtils::GetLocalFilePath(string cloudId,
    string bundleName, int32_t userId)
{
    return GetLocalBucketPath(cloudId, bundleName, userId) + "/" + cloudId;
}
```

代码既没有拒绝 `/` 和 `..`，也没有规范化结果后验证其仍位于预期目录内。操作系统处理路径时会解析这些组件，使最终路径能够越过 bucket 目录。

### 未校验路径到达三个文件系统操作点

已确认的消费者调用链如下：

1. `CloudDiskMetaFile::DoLookup()` 从 dentry 读取 `recordId` 到 `MetaBase::cloudId`。
2. `FileOperationsCloud::DoCloudLookup()` 通过 `InitInodeAttr()` 将该值复制到 `CloudDiskInode::cloudId`。
3. 文件打开或删除流程把该值传给 `GetLocalFilePath()` 或 `GetLocalDKCachePath()`。
4. 构造出的路径未经目录边界检查即进入以下系统调用。

缩略图或 LCD 文件下载成功后，`HandleCloudOpenSuccess()` 对非内容文件构造数据路径和缓存路径。目标路径在 `access(path, F_OK)` 中被判断为不存在时，代码执行：

```cpp
rename(tmpPath.c_str(), path.c_str());
```

如果数据基础目录不存在，或创建 bucket 目录失败，`CheckBucketPath()` 的清理分支还会对同一未校验缓存路径执行：

```cpp
unlink(tmpPath.c_str());
```

常规删除流程中，`FileOperationsCloud::Unlink()` 调用 `DoCloudUnlink()`。后者从 dentry 取得 `cloudId`；当条目是普通文件且存在非纯云端副本时，代码执行：

```cpp
string localPath = CloudFileUtils::GetLocalFilePath(
    cloudId, parentInode->bundleName, data->userId);
unlink(localPath.c_str());
```

### 构建与运行边界

根构建目标 `services_target` 包含 `services/cloudfiledaemon:cloudfiledaemon`。该共享库编译 `file_operations_cloud.cpp`，并依赖 `libdistributedfileutils_lite`；后者编译 `cloud_file_utils.cpp` 和 `meta_file_clouddisk.cpp`。这说明缺陷位于正式服务构建目标，而非测试或示例代码。

`dfs_service_feature_enable_cloud_adapter` 默认关闭；启用后会加入 daemon 的启动配置，并使插件加载器优先尝试云适配器扩展。插件加载器及回退路径还可能加载 `libcloud_adapter.z.so`。实际部署是否启动该功能、安装哪一个插件以及插件如何写入 dentry，均需结合产品配置确认。

相关文件操作由 `cloudfiledaemon` 执行。服务配置使用 uid `1009` 和 SELinux 域 `u:r:cloudfiledaemon:s0`，因此路径遍历不会自动突破该进程已有的 DAC、组权限和 SELinux 限制。

## 影响

在满足触发条件时，恶意 `cloudId` 可以让 `cloudfiledaemon` 对预期 bundle/bucket 目录之外的路径执行操作：

- `DoCloudUnlink()` 和 `CheckBucketPath()` 可删除进程权限范围内的文件。
- `HandleCloudOpenSuccess()` 可把已下载的缓存文件移动到预期数据目录之外的尚不存在位置。
- 目标选择仍受 `cloudId` 长度、目录可遍历性、文件是否存在以及 daemon 的 DAC/SELinux 权限约束。

当前代码在执行 `rename()` 前检查目标路径不存在，所以源码证据不足以声称可稳定覆盖既有文件。源码也未证明普通应用或未认证远程调用方能够直接控制 `cloudId`，不应将影响扩大为任意系统文件操作、权限提升或远程代码执行。

## 触发条件

同时满足以下条件时可到达受影响操作：

1. Cloud Disk/云适配器功能在目标产品中启用，且相关 daemon 与实际数据同步插件已加载。
2. 包含 `/` 和 `..` 路径组件的 `cloudId` 被写入 Cloud Disk dentry。通过仓库内可见 IPC 入口写入时，调用方必须是持有 `ohos.permission.CLOUDFILE_SYNC` 的 system app；实际插件还必须接受并持久化该值。
3. 对于常规删除路径，目标 dentry 必须是普通文件，且 `position != CLOUD`，随后发生对应的 FUSE unlink 操作。
4. 对于下载后移动路径，条目必须是非内容类型，云端读取会话成功，并且目标路径检查结果允许进入 `rename()` 分支。
5. 对于失败清理路径，数据基础目录不存在或 bucket 目录创建失败，随后进入 `CheckBucketPath()` 的清理分支。
6. 逃逸后的父目录可被 daemon 遍历，且目标操作未被 DAC 或 SELinux 拒绝。

## 修复建议

1. 将 `cloudId` 明确定义为不具备路径语义的单一组件。在进入持久化层时使用正向格式规则校验，并拒绝空值、`.`、`..`、任何 `/`、嵌入式 NUL 以及不符合长度或字符集要求的值。所有插件和 IPC 路径应遵循同一规则。
2. 在 `UpdateDentry()` 写入前以及 `DoLookup()` 结果用于文件系统路径前再次校验，以阻止已有异常元数据或其他写入路径绕过入口检查。
3. 路径构造后进行组件级规范化和父目录约束检查，确认结果位于预期数据目录或缓存目录之下。不要使用简单字符串前缀比较判断包含关系。
4. 对删除和移动操作优先使用锚定到可信目录文件描述符的 `unlinkat()`、`renameat()` 等接口，并把 `cloudId` 作为已校验的叶子名称传入。平台支持时可结合 `openat2()` 的目录约束和禁止符号链接选项，减少符号链接与检查后使用竞态带来的绕过空间。
5. 对无法通过新规则的已有 dentry 采用显式错误处理或隔离策略，不要继续将其中的 `cloudId` 传给路径辅助函数。

## 问题概述

DHCP 客户端的 `GetDhcpOption` 支持 Option Overload：当主 options 区域中的 option 52 指出 `file` 或 `sname` 还承载选项时，解析器会把当前扫描指针 `pOption` 切换到相应字段。然而，每次循环开始的 `CheckOptionsData` 和 option 52 的长度检查仍固定从 `packet->options` 读取。

这使得指针已经切换到 `file` 或 `sname` 后，校验的对象仍是主 options 区域。位于扩展字段的有效选项会被误判为不存在，或使用与当前字段无关的长度进行边界判断。合法使用 Option Overload 的服务端因此无法让客户端取得 DNS、路由等扩展配置。

## 协议背景与受影响范围

RFC 2132 第 9.3 节定义 option 52（Option Overload）。当该选项指示 `file` 或 `sname` 字段时，这两个字段不再表示传统引导信息，而是 DHCP 选项扩展空间。解析器必须在选定字段上按该字段的边界扫描。

| 位置 | 当前行为 | 应有行为 |
| --- | --- | --- |
| `CheckOptSoverloaded`，`dhcp_options.cpp:27-43` | 始终取 `packet->options` | 对当前扫描字段进行长度与 option 52 检查 |
| `CheckOptionsData`，`dhcp_options.cpp:46-70` | 始终取 `packet->options` | 检查调用者当前的 `pOption` |
| `GetDhcpOption`，`dhcp_options.cpp:153-203` | 切换 `pOption`，但校验函数不知道这一切换 | 将当前字段与最大长度一起传给校验函数 |

## 根本原因

主循环正确维护了字段状态：

```cpp
const uint8_t *pOption = packet->options;
int nIndex = 0, maxLen = DHCP_OPT_SIZE, nOver = 0, nFinished = 0;
// ...
case END_OPTION:
    if ((nFlag == OPTION_FIELD) && (nOver & FILE_FIELD)) {
        pOption = packet->file;
        nIndex = 0;
        maxLen = DHCP_BOOT_FILE_LENGTH;
        nFlag = FILE_FIELD;
    }
```

但它调用的校验函数自行重新选择了主字段：

```cpp
static int CheckOptionsData(const struct DhcpPacket *packet, int code, int index, int maxLen)
{
    // ...
    const uint8_t *pOption = packet->options;  // 忽略调用方已选中的字段
    if (pOption[index + DHCP_OPT_CODE_INDEX] != code) {
        return DHCP_OPT_NULL;
    }
    // ...
}
```

因此，在进入 `file` 的第一轮时，`GetDhcpOption` 对 `pOption=file` 的 switch 判断与 `CheckOptionsData` 对 `packet->options` 的 code 判断指向两个不同缓冲区。解析状态不能保持一致。

## 正常调用路径与触发链

```text
DHCP 服务端发送合法 DHCPACK / OFFER
  │ 主 options: option 52 = FILE_FIELD，随后 END
  │ file 字段: DNS option 6 = 8.8.8.8，随后 END
  ▼
客户端调用 GetDhcpOptionUint32(packet, DOMAIN_NAME_SERVER_OPTION, ...)
  ▼
GetDhcpOption
  │ 扫描主字段，识别 option 52
  │ 遇到 END 后把 pOption 切换到 packet->file
  ▼
CheckOptionsData(packet, code, nIndex, maxLen)
  │ 又固定读取 packet->options
  ▼
返回“未找到”，DNS 没有进入 DHCP 结果
```

### 最小触发条件

1. DHCP 服务端产生包含合法 option 52 的报文。
2. option 52 指定 `file`、`sname` 或二者为扩展选项字段。
3. 目标选项仅位于被指定的扩展字段中。
4. 客户端通过 `GetDhcpOption` 或其类型封装函数读取该选项。

验证使用主 fields 中 `option 52 = FILE_FIELD` 和一个位于 `file` 中的 DNS option 6，值为 `8.8.8.8`。真实解析器返回 `parsed=0 value=0`；符合协议的扫描应找到该选项。

## 影响分析

### 直接行为

- 扩展字段中的 DNS、路由或其他受支持选项不会被解析。
- 客户端可能取得地址，但没有使用服务端随租约提供的完整配置。
- 解析结果取决于服务端是否将选项放在主 options 区域，造成互操作不一致。

### 用户可见后果

- 在使用 Option Overload 的网络中，设备可能无法解析名称、使用错误路由或缺少预期配置。
- 网络配置看似已获取成功，但连接后续服务时才表现为不可用。
- 同一 DHCP 配置在不使用 Option Overload 的服务端上正常，在使用该标准机制的服务端上失效。

### 边界

本条仅针对扩展字段扫描。主 options 区域内的选项仍按现有路径解析；不应据此推断所有 DHCP 报文都受影响。

## 修复建议

将当前字段指针明确传给两个校验函数，避免在辅助函数中重新固定为 `packet->options`：

```cpp
static int CheckOptionsData(const uint8_t *options, int code, int index, int maxLen)
{
    if (index >= maxLen - DHCP_OPT_DATA_INDEX) {
        return DHCP_OPT_FAILED;
    }
    if (options[index + DHCP_OPT_CODE_INDEX] != code) {
        return DHCP_OPT_NULL;
    }
    // 使用同一 options 指针完成长度检查
}
```

调用处应传入当前 `pOption`。同样应让 option 52 的长度检查使用当前字段，避免未来支持 `sname` 时重现相同问题。

## 回归测试建议

| 用例 | 报文布局 | 期望 |
| --- | --- | --- |
| 主 fields 选项 | DNS 在 `options` | 保持现有解析成功 |
| `FILE_FIELD` | option 52 在 `options`，DNS 在 `file` | 解析到正确 DNS 值 |
| `SNAME_FIELD` | option 52 在 `options`，目标选项在 `sname` | 解析到正确值 |
| 两字段重载 | `file` 与 `sname` 分别有不同选项 | 两个字段均按各自边界扫描 |
| 非法长度 | 扩展字段内 option 长度越界 | 安全拒绝，不读取主 fields 的同索引数据 |

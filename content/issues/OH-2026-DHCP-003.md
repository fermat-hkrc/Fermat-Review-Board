## 问题概述

DHCP 客户端的 GetDhcpOption 已实现 Option Overload 的字段切换：主 options 区域中的 option 52 可以要求继续扫描 file 或 sname 字段。

但是，主循环切换当前扫描指针后，两个辅助校验函数又自行固定为 packet->options。于是主循环读取的是扩展字段，校验函数检查的却仍是主字段；二者不再描述同一段数据。

位于 file 或 sname 中的有效选项会被漏掉。客户端读取 DNS 时走这条通用解析路径，未找到时会转到默认 DNS 配置。

## 源码中的不一致

主循环从主 options 开始：

    const uint8_t *pOption = packet->options;

识别 Option Overload 并遇到 END 后，它会切换到 file：

    pOption = packet->file;
    nIndex = 0;
    maxLen = DHCP_BOOT_FILE_LENGTH;

但 CheckOptionsData 又重新指定主区域：

    const uint8_t *pOption = packet->options;
    if (pOption[index + DHCP_OPT_CODE_INDEX] != code) {
        return DHCP_OPT_NULL;
    }

CheckOptSoverloaded 也有同样的固定指针。扩展字段的状态没有被传入辅助函数。

## 正常调用路径

    DHCP 服务端发送带 Option Overload 的回复
      -> 主 options 的 option 52 指定 FILE_FIELD
      -> file 中携带 DNS option 6
      -> DhcpClientStateMachine::ParseNetworkDnsInfo
      -> GetDhcpOption(packet, DOMAIN_NAME_SERVER_OPTION, ...)
      -> 扫描切换到 file
      -> 校验仍读取主 options
      -> DNS option 未被找到
      -> 使用默认 DNS

Option Overload 是 RFC 2132 定义的报文布局。该路径只要求服务端把目标选项放入它明确声明的扩展字段。

## 最新主线验证

本条在 GitCode master 的 f52429ee1873c13c8ed55bde0cb9914b2dfedc43 上重新构建生产 dhcp_options.cpp。

输入布局为：

    packet.options = [52, 1, FILE_FIELD, END]
    packet.file    = [6, 4, 8, 8, 8, 8, END]

生产 GetDhcpOptionUint32 对 DNS option 的输出为：

    valid overload DNS parsed=0 value=0

符合该布局的解析应找到 8.8.8.8；当前结果没有找到该选项。

## 影响

- 服务端提供的 DNS、路由等扩展选项可能没有进入客户端结果。
- 客户端可取得地址，但网络配置与服务端提供的完整配置不一致。
- 只在主 options 中放置选项的服务端不受这一路径影响，因此表现具有网络环境差异。

## 修复建议

让辅助函数接收当前扫描字段，而不是重新选择 packet->options：

    static int CheckOptionsData(const uint8_t *options, int code,
        int index, int maxLen)

调用点传入当前 pOption。Option Overload 的长度校验也应使用同一个当前字段。

## 回归测试建议

| 报文布局 | 期望 |
| --- | --- |
| DNS 在主 options | 保持现有解析结果 |
| FILE_FIELD 中的 DNS | 找到正确 DNS |
| SNAME_FIELD 中的 DNS | 找到正确 DNS |
| FILE_FIELD 与 SNAME_FIELD 同时使用 | 按各自边界扫描 |
| 扩展字段内长度超界 | 拒绝该字段，不读取主字段同一偏移 |

## 问题概述

Lite DHCP 客户端的 `DhcpClientProxy::StartDhcpClient` 与 `DhcpClientStub::OnStartDhcpClient` 对同一 IPC 请求的字段布局不一致。proxy 在 interface token 与异常占位后直接写入接口名、BSSID 和布尔配置；stub 在读取相同前缀后却先要求一个 `SvcIdentity`。该读取失败时，stub 把失败业务码写入 reply，且不会调用 `StartDhcpClient`。

随后 proxy 只检查 IPC 调用是否返回和 reply 的 `exception` 字段，不检查 `owner.retCode`。于是“请求到达、业务拒绝”的情形会被转换成调用方可见的成功结果。验证中 proxy 返回 0，而服务端 `StartDhcpClient` 调用次数为 0。

## 请求与响应协议对照

### 请求字段

| 顺序 | proxy 写入 | stub 读取 | 后果 |
| ---: | --- | --- | --- |
| 1 | interface token | interface token | 一致 |
| 2 | `int32_t 0` 异常占位 | `int32_t exception` | 一致 |
| 3 | `string ifname` | `SvcIdentity sid` | 错位，`ReadRemoteObject` 失败 |
| 4 | `string bssid` | `string ifname` | 仅在前一项不存在时才会读取 |
| 5+ | 五个 bool 配置 | 其余配置字段 | 同样依赖前一项布局正确 |

proxy 的请求构造：

```cpp
(void)WriteInt32(&req, 0);
(void)WriteString(&req, config.ifname.c_str());
(void)WriteString(&req, config.bssid.c_str());
(void)WriteBool(&req, config.prohibitUseCacheIp);
// 其余 bool 配置
```

stub 的前置读取：

```cpp
ErrCode ret = DHCP_E_FAILED;
SvcIdentity sid;
bool readSid = ReadRemoteObject(req, &sid);
if (!readSid) {
    (void)WriteInt32(reply, 0);
    (void)WriteInt32(reply, ret);
    return DHCP_OPT_FAILED;
}
```

### 响应字段

Lite IPC 回调会从 reply 填充 `owner.exception` 与 `owner.retCode`。proxy 当前只判断前者：

```cpp
if (owner.exception) {
    return DHCP_E_FAILED;
}
return DHCP_E_SUCCESS;       // owner.retCode 被忽略
```

因此，reply 中的业务失败码即使已被正确写入，也不会传递到 API 调用方。

## 正常调用路径与触发链

```text
Lite 上层网络初始化
  │ 调用 DhcpClientProxy::StartDhcpClient(config)
  ▼
proxy 写入 token、异常占位、ifname、bssid、配置
  ▼
DhcpClientStub::OnRemoteRequest
  │ 验证 token 与异常占位
  ▼
DhcpClientStub::OnStartDhcpClient
  │ 将 ifname 所在位置当作 SvcIdentity 读取
  │ ReadRemoteObject 失败，写入业务失败码
  │ 不调用 StartDhcpClient(config)
  ▼
proxy 忽略 owner.retCode
  ▼
上层收到 DHCP_E_SUCCESS，实际客户端未启动
```

### 最小触发条件

1. Lite DHCP Client 服务已注册，proxy 有可用 remote 对象。
2. 上层以正常 `RouterConfig` 调用 `StartDhcpClient`。
3. IPC 传输层本身能够交付请求和 reply。

验证使用真实 Lite proxy、真实 Lite stub 和最小 in-process IPC 边界。记录服务端覆盖实现显示 `server_start_calls=0`，而调用端得到 `proxy_result=0`。替身没有重写 proxy 的序列化、stub 的读取或 reply 的字段处理。

## 影响分析

### 直接行为

- DHCP Client 启动操作没有执行。
- 调用方得到成功返回值，无法基于 API 结果重试或报告失败。
- 网络初始化状态与业务返回值相矛盾。

### 用户可见后果

- 设备可能显示网络初始化已请求成功，但接口没有开始 DHCP 流程。
- 上层状态机不会进入失败或重试分支，网络长期处于未配置状态。
- 日志和 API 结果可能掩盖服务端曾拒绝请求的原因。

### 边界

本条证明的是当前 proxy 与 stub 配对时的正常调用路径。它不需要畸形 IPC 数据，也不依赖远端死亡或传输异常。当前 stub 在读取 `SvcIdentity` 失败后即返回，因此后续配置字段的具体处理不属于这次验证的结论。

## 修复建议

必须同时修复请求契约和响应传播：

1. 如果启动请求需要回调对象，proxy 应在同一字段位置调用 `WriteRemoteObject` 写入合法 `SvcIdentity`；如果不需要，stub 应删除 `ReadRemoteObject`。
2. 在 proxy 成功收到 reply 后检查 `owner.retCode`，并将其返回给调用方。
3. 为请求和 reply 建立每个 command 的字段表，防止同类错位。

示例响应处理：

```cpp
if (owner.exception != 0) {
    return DHCP_E_FAILED;
}
return static_cast<ErrCode>(owner.retCode);
```

## 回归测试建议

| 用例 | 期望 |
| --- | --- |
| 正常 `RouterConfig` 启动 | stub 的 `StartDhcpClient` 被调用一次，proxy 返回其业务结果 |
| 服务端返回业务失败 | proxy 返回同一失败码，不得报告成功 |
| IPC 传输失败 | proxy 返回传输失败码 |
| 缺失或无效 callback identity（若协议要求） | stub 拒绝，proxy 向上层传播失败 |
| 注册回调与启动请求 | 两个 command 的字段顺序各自稳定且互不混用 |

## 问题概述

`NfcTagProxy::WriteNdefTag` 是应用侧写入 NDEF Tag 数据的正常 IPC 入口。服务端 `NfcTagStub::OnWriteNdefTag` 已经取得了实际执行结果 `ret`，但没有把该结果写入 reply，而是把输入字符串长度 `dataLen` 写入了同一字段。客户端随后无条件把该整数解释为 `ErrCode` 返回给调用方。

因此，当写入服务实际成功并返回 `NFC_SUCCESS`（0）时，只要 NDEF 数据长度大于 0，应用就会收到一个由字节长度构成的非零结果。例如长度为 3 的合法数据会得到 `3`，而不是服务实际返回的 `0`。这不是异常输入路径；有效的非空 NDEF 写入即可稳定触发。

## 受影响范围

| 位置 | 角色 | 字段实际含义 | 另一端期望含义 |
| --- | --- | --- | --- |
| `services/src/nfc_tag_stub.cpp:96-110` | 服务端请求处理 | `dataLen`，调用方输入的字符串长度 | `WriteNdefTag` 的 `ErrCode` |
| `interfaces/inner_api/src/nfc_tag_proxy.cpp:111-141` | 客户端 IPC 代理 | 从 reply 读取一个 `int32_t` | `ErrCode` |

同一源文件中的 `OnReadNdefTag`、`OnWriteNdefData` 均把 `ret` 写入 reply，说明 `OnWriteNdefTag` 的行为与相邻 IPC 方法也不一致。

## 根本原因

服务端先校验长度，再调用真正的写入实现。调用的返回值被保存在 `ret` 中，但 reply 使用了不相关的 `dataLen`：

```cpp
// services/src/nfc_tag_stub.cpp
int32_t dataLen = static_cast<int32_t>(dataToWrite.length());
if (dataLen > NFC_TAG_MAX_LEN || dataLen <= 0) {
    return NFC_INVALID_PARAMETER;
}
ErrCode ret = WriteNdefTag(dataToWrite);
reply.WriteInt32(dataLen);       // 写入输入长度，而不是 ret
return ret;
```

客户端传输成功后没有其他结果字段可供读取，直接将这一整数转换为错误码：

```cpp
// interfaces/inner_api/src/nfc_tag_proxy.cpp
int error = Remote()->SendRequest(NFC_TAG_CMD_WRITE_NDEF_TAG, data, reply, option);
if (error != ERR_NONE) {
    return NFC_IPC_SEND_FAILED;
}
return ErrCode(reply.ReadInt32());
```

这里并不是 proxy 的类型转换导致结果失真。问题在于双方没有对 reply 的第一个 `int32_t` 使用相同的字段定义：stub 写入“请求数据长度”，proxy 读取“业务执行结果”。

## 正常调用路径与触发链

```text
应用 / NFC 客户端
  │ 调用 NfcTagProxy::WriteNdefTag(validNdef)
  ▼
NfcTagProxy
  │ 写入 interface token 与 NDEF 字符串
  │ SendRequest(NFC_TAG_CMD_WRITE_NDEF_TAG)
  ▼
NfcTagStub::OnWriteNdefTag
  │ 读取字符串并校验 0 < dataLen <= NFC_TAG_MAX_LEN
  │ WriteNdefTag(dataToWrite)  → 真实服务返回 NFC_SUCCESS
  │ reply.WriteInt32(dataLen)  ← 写错字段
  ▼
NfcTagProxy
  │ reply.ReadInt32() → ErrCode(dataLen)
  ▼
应用得到“失败”结果，尽管写入已完成
```

### 最小触发条件

1. NFC Tag 服务可用，且应用通过公开的 `WriteNdefTag` 路径发起请求。
2. 输入为长度大于 0、未超过 `NFC_TAG_MAX_LEN` 的合法 NDEF 字符串。
3. 服务端的 `WriteNdefTag` 返回成功。
4. 调用方依赖 `NfcTagProxy::WriteNdefTag` 的返回值判断写入是否完成。

没有要求构造损坏 IPC 数据、改变服务状态或访问内部接口。验证使用了 3 字节有效输入，实际服务结果为 0，而客户端收到 3。

## 影响分析

### 直接行为

- 成功写入会被客户端误报为失败。
- 返回值随输入长度变化，不再表示 NFC 服务的业务结果。
- 同一操作可能已经落到 Tag 上，但调用方仍进入错误处理分支。

### 用户可见后果

- 写卡界面可能提示失败，用户重复贴卡或重复点击写入。
- 上层如果对非零返回值重试，可能对同一 Tag 执行多次写入。
- 依赖返回码更新 UI、日志或后续流程的应用会记录与真实状态相反的结果。

### 边界

此问题影响结果一致性，不改变输入长度校验，也不改变服务端 `WriteNdefTag` 自身的执行结果。空字符串和超长字符串会在 stub 的长度校验处提前返回，不属于本条的成功后误报场景。

## 修复建议

服务端 reply 应使用与 proxy 一致的字段定义，即写入真实业务返回值：

```cpp
ErrCode ret = WriteNdefTag(dataToWrite);
reply.WriteInt32(static_cast<int32_t>(ret));
return ret;
```

若协议需要同时返回写入长度，应新增独立字段，并同步更新 proxy；不能复用结果码字段。

## 回归测试建议

| 用例 | 服务实现返回 | 输入 | proxy 期望返回 |
| --- | ---: | --- | ---: |
| 正常写入 | `NFC_SUCCESS` | 3 字节合法 NDEF 数据 | `NFC_SUCCESS` |
| 正常写入 | `NFC_SUCCESS` | 其他合法非零长度数据 | `NFC_SUCCESS`，不得等于长度 |
| 服务失败 | 非零 `ErrCode` | 合法 NDEF 数据 | 与服务端错误码一致 |
| 参数校验失败 | `NFC_INVALID_PARAMETER` | 空或超长数据 | 保持现有参数校验结果 |

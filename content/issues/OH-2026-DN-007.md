## 漏洞概述

通知授权对话框在 `onSizeChange` 回调和跨越 `await` 的生命周期更新流程中调用全局 `getContext`。ArkUI 接口文档明确说明：该接口用于异步回调，或初始调用不在当前页面时，可能无法沿调用链找到实例上下文并返回 `undefined`。当前代码通过类型断言把返回值视为 `UIAbilityContext`，随后立即读取 `context.config` 或 `resourceManager`，没有运行时缺失值检查。

本报告保留 7 个经过调用环境复核的风险位置：一个共享辅助函数中的直接解引用，以及六个处于真实异步或生命周期路径的直接调用表达式。另有 11 个只在同步 `build` 或样式构建阶段执行的位置；这些位置没有满足接口文档描述的异步上下文丢失前提，因此没有纳入本报告。

相关页面进入 `enable_notification_dialog_hap` 的 ArkTS 构建，并由组件 `service_group` 纳入产品。当前 `master` 提交 `c76a751c286e4e3fc614b4fccd57dfbfa13d2aa3` 仍存在全部七处。逐文件检查确认 `OpenHarmony-v6.0-Release` 也包含这七处；由于仓库缺少可用于连续比较的中间公开标签，未进一步推断最早受影响版本。

本次没有动态制造 Context 跟踪失败。当前证据能够确认缺失值处理不完整，但尚未确认普通应用可以稳定控制 Context 丢失或造成进程级拒绝服务。

## 根本原因

### 两个辅助函数假定 Context 始终存在

**位置**: `services/dialog_ui/enable_notification_dialog/entry/src/main/ets/common/utils.ets:79`

```typescript
export function getFontSizeScale(context: common.UIAbilityContext, maxScale: number = 3.2): number {
  let fontSizeScale = context.config?.fontSizeScale;
  if(fontSizeScale === undefined) {
    return Constants.FONT_SCALE_DEFAULT;
  }
  return fontSizeScale > maxScale ? maxScale : fontSizeScale;
}

export function sourceToVp(source: Resource): number {
  return px2vp(getContext().resourceManager.getNumber(source.id));
}
```

`getFontSizeScale` 的参数类型不包含 `undefined`，但调用方使用 `getContext(this) as common.UIAbilityContext` 进行编译期断言。该断言不会在运行时检查返回值。`sourceToVp` 则在函数内部无参数调用 `getContext()` 并立即读取 `resourceManager`。

当前 ArkUI 接口声明的文档说明，默认 Context 依赖调用链追踪；在异步回调中可能追踪失败并返回 `undefined`。同一声明已建议改用 `UIContext.getHostContext`。

### 七个保留位置均有异步或生命周期依据

1. `common/utils.ets:88-90`：`sourceToVp` 直接读取 `getContext().resourceManager`。该辅助函数分别由 `notificationDialog.ets:167` 和 `pcNotificationDialog.ets:175` 的标题 `onSizeChange` 回调调用，两个调用共享同一处根因，因此按一个位置计数。
2. `notificationDialog.ets:168`：标题 `onSizeChange` 回调把 `getContext(this)` 直接传给 `getFontSizeScale`。
3. `pcNotificationDialog.ets:176`：PC 标题 `onSizeChange` 回调采用相同调用方式。
4. `carNotificationDialog.ets:114`：车机标题 `onSizeChange` 回调采用相同调用方式。
5. `carNotificationDialog.ets:139`：车机正文 `onSizeChange` 回调采用相同调用方式。
6. `notificationDialog.ets:377`：`updateButtomVisibility` 计算“禁止”按钮文本宽度时直接传入 `getContext(this)`。
7. `notificationDialog.ets:386`：同一函数计算“允许”按钮文本宽度时再次直接传入 `getContext(this)`。

第 6、7 处由 `updateStatus` 调用。`updateStatus` 在调用前依次等待 `updateApplicationName` 和 `updateIsBottomPopover`，并且自身从异步 `aboutToAppear`、`updateOnPageShow` 以及折叠显示回调进入。因此这两个位置已经跨越异步边界，不属于同步页面构建表达式。

典型标题回调如下：

```typescript
.onSizeChange((oldValue: SizeOptions, newValue: SizeOptions) => {
  let options: MeasureOptions = {
    textContent: $r('app.string.group_label_notification', this.appName),
    fontSize: getLimitFontSize(sourceToVp($r('sys.float.ohos_id_text_size_headline8')),
      getFontSizeScale(getContext(this) as common.UIAbilityContext, Constants.FONT_SCALE_MAX)),
    fontWeight: FontWeight.Bold,
  };
  this.titleContainerWidth = calContainerWidth(newValue.width as number, options,
    Constants.CROSS_LINE_RATIO, this.getUIContext().getMeasureUtils());
})
```

## 影响

- 标题或正文的 `onSizeChange` 回调可能在读取 `resourceManager` 或 `context.config` 时停止，导致宽度、对齐方式或超长文本状态没有按新尺寸更新。
- `updateButtomVisibility` 在异常发生后由自身的 `try/catch` 记录错误并退出，按钮单行或双行布局可能继续保留旧状态。
- 该缺陷位于系统通知授权对话框，可能造成特定设备形态、字体缩放或窗口变化下的页面显示异常。

当前证据不支持通知权限绕过、敏感信息泄露或稳定进程崩溃结论。ArkUI 文档描述的是 Context “可能”追踪失败；实际发生仍取决于组件生命周期和回调调度状态。

## 触发条件

1. 通知授权对话框加载默认、PC 或车机页面之一。
2. 标题或正文触发 `onSizeChange`，或者默认页面在生命周期更新中执行跨越 `await` 的 `updateStatus`。
3. ArkUI 无法为该异步调用追踪到当前组件实例的 Context，并让 `getContext` 返回 `undefined`。
4. 代码在没有检查的情况下读取 `resourceManager` 或进入 `getFontSizeScale` 读取 `context.config`。

页面需要仍处于足以执行回调的状态，但 Context 已无法被接口追踪。尚未确认外部调用者能够稳定安排这一时序。

## 修复建议

建议在组件方法中通过 `this.getUIContext().getHostContext()` 获取宿主 Context，并把结果保存到局部变量后进行显式检查。不要使用类型断言把可能缺失的结果直接收窄为 `UIAbilityContext`：

```typescript
let hostContext = this.getUIContext().getHostContext();
if (hostContext === undefined) {
  console.error(TAG, 'host context is unavailable');
  return;
}
let fontScale = getFontSizeScale(hostContext as common.UIAbilityContext, Constants.FONT_SCALE_MAX);
```

`sourceToVp` 应改为接收调用方已经验证的 `resourceManager` 或 Context，而不是在辅助函数内部重新调用全局 `getContext()`。对两个按钮的测量应在一次 Context 检查后复用同一值。若组件已离开页面，应安全结束本次布局更新并保留可预测的默认字体和布局状态。

## 漏洞概述

Cloud Media `CloudOpen` 在 `cacheLock` 写锁下向 `cloudFdCache` 插入 handle，离开临界区后又使用 `operator[]` 访问同一个 `std::map`。FUSE 使用多线程请求循环，其他 open/release 请求能够在该无锁查找期间插入或删除节点。

## 根本原因

**位置**：`services/cloudfiledaemon/src/fuse_manager/fuse_manager.cpp`

```cpp
{
    std::unique_lock lock(data->cacheLock);
    data->cloudFdCache[fi->fh] = cloudFdInfo;
}
return CloudOpenHelper(data->cloudFdCache[fi->fh]); // 无锁树查找
```

无锁访问不是使用已经取得的独立元素引用，而是重新遍历可能正在修改或重平衡的 `std::map` 内部结构。

## 影响

- `cloudfiledaemon` 中发生未定义行为、错误 `shared_ptr` 或进程崩溃。
- 一个调用者可影响共享 daemon 服务的其他 Cloud Media 用户。
- 并发 release 还可以让无锁查找与节点删除重叠。

## 触发条件

具备 Cloud Media 文件访问权的进程并发打开多个文件，或让 open 与 release 请求重叠。多线程 FUSE loop 会在不同工作线程处理这些请求。

## 修复建议

在 `cacheLock` 内保存新插入元素的 `shared_ptr` 并将局部副本传给 `CloudOpenHelper`。所有 map 查找、插入和删除都必须使用同一把锁。

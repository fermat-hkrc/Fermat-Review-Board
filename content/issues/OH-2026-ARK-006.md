## 漏洞概述

`SelectionMenu` 只判断传入的 `RichEditorController` JavaScript wrapper 是否非空，随后直接读取 `getSelection()` 返回值的 `.selection` 属性。wrapper 可以已经创建但尚未绑定 native controller，也可以在原 RichEditor 被销毁后继续存活；这两种情况下，动态桥接层会在没有设置返回值的情况下结束调用，因此 JavaScript 收到 `undefined`。`SelectionMenu` 随后的属性访问会抛出异常，使选择菜单无法完成初始化。

这是一个需要应用组件生命周期配合的本地可用性问题，不是普通空编辑器即可触发的问题。当前证据也不支持内存破坏、权限提升或跨应用影响。我核对了提交 `d8847980b8c1fdbb6e79b5a9b641cabde4ba9a70` 的构建输入、动态桥接实现和相关历史，但没有执行设备侧复现。因此建议按 LOW、CWE-476 提交。

## 根本原因

### 实际发布模块直接解引用返回值

`advanced_ui_component/selectionmenu/interfaces/BUILD.gn` 将 `interfaces/selectionmenu.js` 编译为 `selectionmenu.abc`，并嵌入 `arkui.advanced.SelectionMenu` 共享库。实际进入 ABC 的 `SelectionMenuComponent.aboutToAppear` 如下：

```javascript
aboutToAppear() {
    if (this.controller) {
        let richEditorSelection = this.controller.getSelection();
        let start = richEditorSelection.selection[0];
        let end = richEditorSelection.selection[1];
        // ...
    }
}
```

这里的检查只能证明 wrapper 存在，不能证明 wrapper 内的 native controller 仍然有效。`updateMenuItemVisibility` 以及剪切、复制、粘贴和全选处理函数中还有五处同样只检查 wrapper 的 `getSelection()` 调用；native controller 在菜单显示后失效时，这些调用也缺少统一的返回值检查。

### 动态桥在 native controller 不可用时返回 undefined

`frameworks/bridge/declarative_frontend/jsview/js_richeditor.h` 中，JavaScript wrapper 只以弱引用保存 native controller：

```cpp
WeakPtr<RichEditorBaseControllerBase> controllerWeak_;
```

公开构造函数创建 wrapper 时不会初始化该弱引用。RichEditor 创建后，`rich_editor_dynamic_modifier.cpp` 才调用 `SetController` 完成绑定。native controller 由 `RichEditorPattern` 持有，因此原 RichEditor 生命周期结束后，仍被应用保存的 JavaScript wrapper 也可能无法再升级这个弱引用。

`frameworks/bridge/declarative_frontend/jsview/js_richeditor.cpp` 的动态 `GetSelection` 在升级或类型转换失败时直接返回：

```cpp
void JSRichEditorController::GetSelection(const JSCallbackInfo& args)
{
    auto controller = controllerWeak_.Upgrade();
    auto richEditorController = AceType::DynamicCast<RichEditorControllerBase>(controller);
    CHECK_NULL_VOID(richEditorController);
    // ...
    args.SetReturnValue(JSRichEditor::CreateJSSelection(value, envFontScale));
}
```

失败分支没有调用 `args.SetReturnValue`，对应 JavaScript 返回 `undefined`。随后 `aboutToAppear` 读取 `richEditorSelection.selection`，形成确定的空值属性访问。

该行为可追溯到 SelectionMenu 于 2023 年 11 月加入仓库时的实现，`weekly_20240115-v` 代码快照也包含相同调用链。仓库现有标签不足以把这些提交可靠映射为正式发布版本，因此本报告只把当前提交列为已确认受影响版本，也没有声称存在已发布修复。

### 空 Span 查询不是本报告的问题

在 controller 有效时，动态 `GetSpansInfo` 会调用 `CreateJSSpansInfo`。该函数先创建 `JSArray`，即使查询结果没有任何 Span，也会返回长度为 0 的数组。因此，空编辑器或空范围查询不会因为 `.length` 访问而触发本问题。

controller 无效时 `getSpans()` 也可能没有返回值，但 `aboutToAppear` 会先在 `getSelection()` 的 `.selection` 访问处失败。故本报告仅保留 `getSelection()` 返回 `undefined` 的路径，不把合法空 Span 结果列为另一项漏洞。

## 影响

- SelectionMenu 在 `aboutToAppear` 阶段抛出 JavaScript 空值属性访问异常，菜单初始化失败。
- 如果 native controller 在菜单存活期间失效，后续布局更新或菜单操作也可能遇到同类异常。
- 异常是否只终止当前组件构建、影响页面，或进一步导致应用退出，取决于宿主运行时的异常处理；本次源码复核没有验证更强影响。

受影响边界限于使用该 controller 的应用自身可用性。没有证据表明外部应用或远程输入可以直接构造所需生命周期状态。

## 触发条件

需要同时满足以下条件：

1. 应用向 `SelectionMenu` 传入一个非空 `RichEditorController` wrapper。
2. 菜单调用 `aboutToAppear` 或后续刷新函数时，该 wrapper 尚未绑定 RichEditor 创建的 native controller，或原 RichEditor 已销毁并使弱引用失效。
3. `getSelection()` 经动态桥返回 `undefined`。
4. SelectionMenu 未检查该返回值，继续访问 `.selection`。

正常绑定且仍存活的 RichEditor 不满足第二项。正常空编辑器也不满足第二项，因为有效 controller 仍会返回包含 `selection` 和 `spans` 的对象。

## 修复建议

在 `aboutToAppear`、`updateMenuItemVisibility` 和四个菜单操作处理函数中统一检查 `getSelection()` 的实际返回值。native controller 不可用时，应禁用相关操作并安全返回，而不是继续读取属性。例如：

```javascript
const richEditorSelection = this.controller.getSelection();
if (!richEditorSelection) {
    this.cutAndCopyEnable = false;
    this.visibilityValue = Visibility.None;
    return;
}

const start = richEditorSelection.selection[0];
const end = richEditorSelection.selection[1];
```

建议把检查封装为组件内部辅助函数，避免六个调用点出现不同处理。动态桥也可以在 controller 不可用时返回结构完整的安全默认值，或通过明确的异常/错误契约通知调用方；无论选择哪种接口约定，调用方和接口声明必须一致。

回归测试至少应覆盖：未绑定 wrapper、RichEditor 销毁后仍持有 wrapper、有效空编辑器、有效非空选择，以及菜单显示后的布局刷新。有效空编辑器测试还应确认 `getSpans()` 返回空数组，以防把合法空结果再次误判为 `undefined`。

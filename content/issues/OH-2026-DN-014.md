## 漏洞概述

三类通知克隆恢复服务都在取得各自 `lock_` 前，把 `bundlesInfo_.size()` 或 `priorityInfo_.size()` 作为日志参数。用户切换、恢复和清理路径会在锁内修改相同容器，因此这三处日志读取存在同根因的数据竞争。

## 根本原因

**位置**：

- `services/ans/src/clone/dh_notification_clone_bundle_service.cpp`
- `services/ans/src/clone/notification_clone_bundle_service.cpp`
- `services/ans/src/clone/notification_clone_priority_service.cpp`

```cpp
ANS_LOGI("restore size=%{public}zu", bundlesInfo_.size()); // 锁外读取
std::lock_guard lock(lock_);
// 查找、删除或更新 bundlesInfo_
```

日志参数在进入临界区前求值。真正的业务查找和修改虽然受锁保护，锁外 size 仍与并发修改冲突。

## 影响

- 三处日志可能记录过期或不一致的克隆恢复数量。
- 无锁读取容器元数据构成 C++ 数据竞争。
- 后续业务操作仍在锁下，因此当前主要影响是诊断错误和低概率运行异常。

## 触发条件

克隆恢复事件与用户切换、数据清理或另一恢复步骤并发，使一个线程记录 size 时另一个线程清空、填充或删除对应容器。

## 修复建议

在各自 `lock_` 下取得 size 快照，再在临界区外记录快照；或者把日志移到已经持锁的代码段。三个类应采用一致修复。

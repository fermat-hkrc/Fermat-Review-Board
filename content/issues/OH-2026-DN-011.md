## 漏洞概述

`DistributedClient::AddDevice`、`ReleaseDevice` 和 `RefreshDevice` 在 `clientLock_` 下修改 `networksId_`，但 `GetSocketId` 在查询另一张 map 后释放锁，再无锁查找和读取 `networksId_`。配对设备离线回调与操作回复路径可在不同队列并发执行，删除当前 iterator 指向的节点。

## 根本原因

**位置**：`services/distributed/src/base/distributed_client.cpp`

```cpp
{
    std::lock_guard lock(clientLock_);
    // 查询 socketsId_
}
auto iter = networksId_.find(deviceId); // 未持有 clientLock_
return iter->second;                    // 节点可能已被 erase
```

设备生命周期任务和分布式通知操作任务分别运行在 `distributedQueue_` 与 `serviceQueue_`。两条队列不会互相串行化。

## 影响

- `erase(deviceId)` 可使 `GetSocketId` 已取得的 map iterator 失效。
- 随后的 `iterator->second` 访问已经释放的节点，可能导致通知服务进程崩溃。
- 共享分布式通知功能可被拒绝服务。

## 触发条件

已配对远端发送需要本机回复的通知操作，随后立即断开连接。操作回复路径调用 `SendMessage`/`GetSocketId` 的同时，设备离线任务调用 `ReleaseDevice` 删除相同 network ID。

## 修复建议

在 `clientLock_` 下完成 `networksId_` 的查找和值复制，再释放锁。不要把 map iterator 或节点引用带出临界区。也可以把 socket ID 与 network ID 合并为一次受锁快照查询。

## 漏洞概述

`NapiGetAllSubscriptionBundles` 在堆上分配异步调用上下文并创建 Promise，随后调用 `napi_create_async_work` 和 `napi_queue_async_work_with_qos`。代码没有检查这两个 API 的返回状态，却把上下文的释放完全交给异步完成回调。

若异步工作创建失败，完成回调不会取得该上下文；若创建成功但排队失败，已创建的 `napi_async_work` 和上下文也没有错误路径清理。调用返回的 Promise 同时可能一直处于未完成状态。单次泄漏较小，但运行时资源不足或环境关闭等失败持续出现时，重复调用会累积原生堆对象和异步资源。

该函数由 `notificationExtensionSubscription.getAllSubscriptionBundles()` 直接调用，并编译进 `notificationextensionsubscription` 共享库。当前 `master` 提交 `c76a751c286e4e3fc614b4fccd57dfbfa13d2aa3` 仍存在该问题。函数及当前错误处理方式由提交 `420ea2a1366975181b2971e806bc47de78c7528b` 于 2025-09-19 引入；本地公开标签均早于该提交，因此受影响发行标签尚未确认。

## 根本原因

### 创建和排队结果均被忽略

**位置**: `frameworks/js/napi/src/extension_subscription/napi_notification_extension.cpp:1130`

```cpp
AsyncCallbackInfoNotificationExtensionUserGranted* asynccallbackinfo = new (std::nothrow)
    AsyncCallbackInfoNotificationExtensionUserGranted { .env = env, .asyncWork = nullptr };
if (!asynccallbackinfo) {
    Common::NapiThrow(env, ERROR_INTERNAL_ERROR);
    return Common::JSParaError(env, nullptr);
}
napi_value promise = nullptr;
Common::PaddingCallbackPromiseInfo(env, nullptr, asynccallbackinfo->info, promise);

// ...
napi_create_async_work(env,
    nullptr,
    resourceName,
    /* execute callback */,
    AsyncCompleteCallbackRetrunBundleOptionArray,
    (void *)asynccallbackinfo,
    &asynccallbackinfo->asyncWork);

napi_queue_async_work_with_qos(env, asynccallbackinfo->asyncWork, napi_qos_user_initiated);
return promise;
```

两个 N-API 调用都返回 `napi_status`，但函数没有保存或判断结果。创建失败时 `asyncWork` 仍为 `nullptr`，代码还会继续尝试排队；排队失败时函数仍把 Promise 返回给上层。

### 清理只存在于完成回调

**位置**: `frameworks/js/napi/src/extension_subscription/napi_notification_extension.cpp:490`

```cpp
void AsyncCompleteCallbackRetrunBundleOptionArray(napi_env env, napi_status status, void *data)
{
    // ...
    Common::CreateReturnValue(env, asynccallbackinfo->info, result);
    if (asynccallbackinfo->info.callback != nullptr) {
        napi_delete_reference(env, asynccallbackinfo->info.callback);
    }
    napi_delete_async_work(env, asynccallbackinfo->asyncWork);
    delete asynccallbackinfo;
}
```

正常排队并执行完成回调时，异步工作和上下文都会释放。创建或排队失败不会进入该完成路径，调用函数中又没有对应清理分支，因此所有权在失败点丢失。

`frameworks/js/napi/src/extension_subscription/BUILD.gn` 将该文件编译进 `notificationextensionsubscription`。组件构建组通过 `napi_extension_subscription` 将该共享库列入产品框架构建。

## 影响

- 每次失败会遗留一个 `AsyncCallbackInfoNotificationExtensionUserGranted` 上下文；排队失败还会遗留已经创建的 `napi_async_work`。
- 返回给 ArkTS 的 Promise 可能不再被 resolve 或 reject，使调用方持续等待。
- 在持续资源不足或运行环境退出期间反复调用时，原生内存和运行时资源可能逐步增长，影响进程稳定性。

当前只确认了静态失败路径，没有执行 N-API 故障注入或测量单次泄漏大小。尚未证明普通应用能够稳定制造创建或排队失败，也没有证据支持跨进程影响、权限提升或稳定拒绝服务。

## 触发条件

1. ArkTS 调用 `notificationExtensionSubscription.getAllSubscriptionBundles()`。
2. 上下文分配及 Promise 创建成功。
3. `napi_create_async_work` 返回非 `napi_ok`，或创建成功后 `napi_queue_async_work_with_qos` 返回非 `napi_ok`。
4. 代码忽略失败并返回，完成回调没有机会接管和释放上下文。

这些失败通常与 N-API 环境状态或资源不足有关。当前没有确认可由传入业务参数直接控制的失败条件。

## 修复建议

逐步检查资源名创建、异步工作创建和排队操作的 `napi_status`。只有排队成功后才把上下文所有权移交给完成回调。

创建失败时应释放上下文并同步抛出错误或 reject Promise。排队失败时还应先调用 `napi_delete_async_work`，再释放上下文并结束 Promise。可以使用 `std::unique_ptr` 暂时持有上下文，在排队成功后调用 `release()`，避免新增分支遗漏清理。

```cpp
std::unique_ptr<AsyncCallbackInfoNotificationExtensionUserGranted> context(
    new (std::nothrow) AsyncCallbackInfoNotificationExtensionUserGranted { .env = env, .asyncWork = nullptr });
// 检查分配和 Promise 创建。

napi_status status = napi_create_async_work(env, nullptr, resourceName,
    execute, AsyncCompleteCallbackRetrunBundleOptionArray,
    context.get(), &context->asyncWork);
if (status != napi_ok) {
    // reject 或抛出错误；context 自动释放。
    return Common::NapiGetUndefined(env);
}
status = napi_queue_async_work_with_qos(env, context->asyncWork, napi_qos_user_initiated);
if (status != napi_ok) {
    napi_delete_async_work(env, context->asyncWork);
    // reject 或抛出错误；context 自动释放。
    return Common::NapiGetUndefined(env);
}
context.release();
```

## 问题概述

标准版本 DHCP Server 的回调通道存在三处已经实现但无法正确传递的业务事件。

- `OnServerSuccess` 的 proxy 在 IPC 数据中依次写入异常占位值、接口名、设备数量和设备列表；stub 却在读取异常占位值后先把下一个字段当作设备数量，再读取接口名。字段偏移导致注册回调看到错误的接口名和设备数。
- `OnServerLeasesChanged` 在 proxy 中只有日志和 `return`，没有构造请求或调用 `SendRequest`。
- `OnServerSerExitChanged` 同样直接返回，因此退出事件不会离开 proxy。

这三条路径均由 DHCP Server 的正常状态变化触发。已注册回调的管理界面或上层服务无法可靠地收到设备上线、租约变化和服务退出信息。

## 协议字段对照

### `OnServerSuccess` 的实际字段顺序

| 顺序 | proxy 写入 | stub 读取 | 结果 |
| ---: | --- | --- | --- |
| 1 | interface token | interface token（框架分发） | 一致 |
| 2 | `int32_t 0`（异常占位） | 由公共分发逻辑读取 | 一致 |
| 3 | `std::string ifname` | `int size = ReadInt32()` | 错位 |
| 4 | `int stationInfos.size()` | `std::string ifName = ReadString()` | 错位 |
| 5 | 每个站点的三个字符串 | 按错误 `size` 继续读取 | 后续字段继续偏移 |

生产 proxy 的写入顺序：

```cpp
data.WriteInt32(0);
data.WriteString(ifname);
data.WriteInt32(stationInfos.size());
for (auto stationInfo: stationInfos) {
    data.WriteString(stationInfo.deviceName);
    data.WriteString(stationInfo.macAddr);
    data.WriteString(stationInfo.ipAddr);
}
```

生产 stub 的读取顺序：

```cpp
int size = data.ReadInt32();
if (size < 0 || size > MAXIMUM_SIZE) {
    return DHCP_E_SUCCESS;
}
std::string ifName = data.ReadString();
```

字符串序列化的首字节被当作整数大小后，stub 的后续读取位置已经偏离。验证中 proxy 发送 `ifname="wlan0"` 和一个设备，stub 实际收到空接口名与 6 个设备槽位。

## 未发送的两个事件

```cpp
void DhcpServerCallbackProxy::OnServerLeasesChanged(
    const std::string& ifname, std::vector<std::string>& leases)
{
    DHCP_LOGI("DhcpServerCallbackProxy::OnServerLeasesChanged");
    return;
}

void DhcpServerCallbackProxy::OnServerSerExitChanged(const std::string& ifname)
{
    DHCP_LOGI("DhcpServerCallbackProxy::OnServerSerExitChanged");
    return;
}
```

对应 stub 方法也仅向 reply 写入 0 并返回；即使未来 proxy 补发请求，stub 仍需补上字段读取和 `OnServerLeasesChanged` / `OnServerSerExitChanged` 的实际分发。

## 正常调用路径与触发链

```text
DHCP Server 状态变化
  ├─ 站点上线 → DhcpServerCallbackProxy::OnServerSuccess
  │    ├─ 写入 ifname、设备数、设备信息
  │    └─ SendRequest
  │         → DhcpServreCallBackStub::RemoteOnServerSuccess
  │             ├─ 先读取 size，再读取 ifName（与发送端相反）
  │             └─ 回调收到偏移后的数据
  ├─ 租约变化 → OnServerLeasesChanged
  │    └─ 直接 return，注册回调不执行
  └─ 服务退出 → OnServerSerExitChanged
       └─ 直接 return，注册回调不执行
```

### 最小触发条件

1. 标准 DHCP Server 回调对象已注册。
2. 发生至少一个正常事件：站点上线、租约变化或服务退出。
3. 事件经过 `DhcpServerCallbackProxy` 到应用侧 `DhcpServreCallBackStub`。

不需要伪造 IPC 数据。验证使用真实 proxy、真实 stub、一个站点和 in-process IPC 边界，分别调用三种公开回调方法。

## 影响分析

### 站点上线事件

- 接口名可能为空或错误。
- 站点数量来自字符串的序列化数据，不再等于实际 vector 长度。
- 之后的站点字符串按错误数量继续读取，回调消费者不能可靠使用结果。

### 租约和退出事件

- 回调订阅者得不到租约更新通知。
- DHCP Server 退出时，上层无法按事件更新状态或清理显示。
- 代理日志会显示方法被调用，容易掩盖事件没有真正送达的事实。

### 边界

本条确认的是 callback IPC 交付层行为，不依赖 DHCP 租约分配逻辑。错误发生在服务端事件已经决定需要通知上层之后。

## 修复建议

1. 为 `OnServerSuccess` 固定单一协议顺序。最小修复是将 stub 改为先读 `ifName`，再读 `size`；也应检查公共分发层的异常字段与每个 method 的契约。
2. 为 `OnServerLeasesChanged` 和 `OnServerSerExitChanged` 实现完整 proxy 序列化、`SendRequest`、reply 检查和 stub 分发。
3. 为每个 callback code 建立同一份字段序列说明，避免 proxy 和 stub 各自维护隐式顺序。

示例修复方向：

```cpp
// RemoteOnServerSuccess
std::string ifName = data.ReadString();
int size = data.ReadInt32();
if (size < 0 || size > MAXIMUM_SIZE) {
    reply.WriteInt32(0);
    return DHCP_E_SUCCESS;
}
```

## 回归测试建议

| 事件 | 输入 | 期望 |
| --- | --- | --- |
| `OnServerSuccess` | `ifname="wlan0"`、1 个站点 | 回调得到 `wlan0` 与恰好 1 个相同站点 |
| `OnServerSuccess` | 0 个站点 | 回调得到正确接口名和空列表 |
| `OnServerLeasesChanged` | 一个 lease 字符串 | 已注册回调调用 1 次，字段完整 |
| `OnServerSerExitChanged` | `ifname="wlan0"` | 已注册回调调用 1 次，接口名一致 |

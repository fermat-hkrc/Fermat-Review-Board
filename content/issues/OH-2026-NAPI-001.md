## 漏洞概述

`NativeModuleManager` 使用成员 `prefix_` 和 `isAppModule_` 保存当前模块加载的路径前缀和模块类型。缓存未命中时，`LoadNativeModuleWithErrorInfo()` 在 `mutex_` 保护下写入这两个字段；`GetModuleFileName()` 读取 `prefix_` 时不持有任何锁；`Register()` 则在另一把 `nativeModuleListMutex_` 下读取两个字段。

所有 `NativeEngine` 实例，包括 worker runtime，都会引用进程内同一个 `NativeModuleManager` 单例。因此，一个线程加载未缓存模块时，另一个引擎线程可以同时查询模块文件名。不同锁或无锁访问不能建立 C++ 的 happens-before 关系，形成对 `std::string prefix_` 和 `bool isAppModule_` 的数据竞争。

该竞态可确定的影响是未定义行为以及模块名称、类型和路径解析状态不一致。现有代码不能证明竞态能够稳定触发崩溃或造成跨应用模块加载，因此严重程度定为 MEDIUM。

受影响版本仅在 frontmatter 中标记当前 master commit。相同的非统一同步模式还存在于 `master-v`、`weekly_20240115-v` 和 `OpenHarmony-v6.0-Beta1` tag；这些快照只能证明相应版本包含该模式，不能证明首个受影响发布版本。

## 根本原因

### 共享字段和锁没有建立一致的所有权关系

**位置**: `module_manager/native_module_manager.h:197`

```cpp
std::mutex nativeModuleListMutex_;
NativeModule* headNativeModule_ = nullptr;
NativeModule* tailNativeModule_ = nullptr;
std::string loadingModuleKey_;

static std::atomic<NativeModuleManager*> instance_;
pthread_mutex_t mutex_;
std::string prefix_;
bool isAppModule_ = false;
```

`prefix_` 和 `isAppModule_` 是普通非原子成员。声明中没有指定哪一把锁保护它们，实际调用点也采用了三种不同的同步方式。

### 模块加载在 `mutex_` 下写入

**位置**: `module_manager/native_module_manager.cpp:943`

```cpp
if (nativeModule == nullptr) {
    (void)pthread_mutex_lock(&mutex_);
    // 重新检查缓存
    if (nativeModule == nullptr) {
        prefix_ = prefixTmp;
        isAppModule_ = isAppModule;
        g_isLoadingModule = true;
        nativeModule = FindNativeModuleByDisk(moduleName, prefix_.c_str(), relativePath, internal,
            isAppModule, errInfo, loadErrInfo, nativeModulePath, cacheNativeModule);
        g_isLoadingModule = false;
    }
    (void)pthread_mutex_unlock(&mutex_);
}
```

`mutex_` 可以串行化多个缓存未命中的加载操作，但它只能保护同样持有该锁的访问者。其他函数没有一致使用这把锁。

### 文件名查询无锁读取 `prefix_`

**位置**: `module_manager/native_module_manager.cpp:294`

```cpp
std::string NativeModuleManager::GetModuleFileName(const char* moduleName, bool isAppModule)
{
    if (moduleName == nullptr) {
        return "";
    }

    std::string loadPath;
    std::string name = isAppModule ? (prefix_ + "/" + moduleName) : moduleName;
    // 使用 name 查询模块缓存并构造返回路径
}
```

当 `isAppModule` 为 `true` 时，该函数会复制并拼接 `prefix_`。如果另一个线程正在执行 `prefix_ = prefixTmp`，标准库字符串的内部状态会被并发读写，属于 C++ 数据竞争和未定义行为。即使没有崩溃，查询也可能使用另一个模块加载留下的前缀，导致缓存查询失败或返回错误的文件路径。

该读取可以从公开 N-API 到达：

**位置**: `native_engine/native_node_api.cpp:601`

```cpp
NAPI_EXTERN napi_status node_api_get_module_file_name(napi_env env, const char** result)
{
    CHECK_ENV(env);
    CHECK_ARG(env, result);
    auto engine = reinterpret_cast<NativeEngine*>(env);
    *result = engine->GetModuleFileName();
    return napi_clear_last_error(env);
}
```

该入口没有为全局模块管理器加锁。每个引擎只缓存自己的最终文件名，但首次查询仍会进入共享管理器。

### `Register()` 使用了不能保护加载上下文的另一把锁

**位置**: `module_manager/native_module_manager.cpp:340`

```cpp
void NativeModuleManager::Register(NativeModule* nativeModule)
{
    if (nativeModule == nullptr) {
        return;
    }

    std::lock_guard<std::mutex> lock(nativeModuleListMutex_);
    const char* nativeModuleName = nativeModule->name == nullptr ? "" : nativeModule->name;
    std::string appName = prefix_ + "/" + nativeModuleName;
    std::string tmpName = isAppModule_ ? appName : nativeModuleName;
    // 将 tmpName 和 isAppModule_ 写入模块链表
}
```

`nativeModuleListMutex_` 保护模块链表，但写入 `prefix_` 和 `isAppModule_` 的加载路径并不持有这把锁，所以它不能同步这两个字段。常规动态库构造函数在 `FindNativeModuleByDisk()` 内同步注册时，调用线程可能已经持有外层 `mutex_`；但 `napi_module_register()` 和 `napi_module_with_js_register()` 是公开入口，`Register()` 自身没有要求或检查调用方持有该锁。当前正确性依赖调用栈约定，而不是由共享字段的同步机制保证。

### 多个引擎共享同一个管理器

**位置**: `native_engine/native_engine.cpp:189`

```cpp
void NativeEngine::InitWithoutUV()
{
    moduleManager_ = NativeModuleManager::GetInstance();
    referenceManager_ = new NativeReferenceManager();
    callbackScopeManager_ = new NativeCallbackScopeManager();
    tid_ = pthread_self();
}
```

主引擎和 worker 引擎初始化时都会取得同一个单例。模块加载和文件名查询分别通过各自的 `NativeEngine` 执行，但最终读写的是同一组 `NativeModuleManager` 成员，因此引擎级线程约束不能消除该竞态。

## 影响

- 并发读写 `std::string prefix_` 产生 C++ 未定义行为，可能表现为进程崩溃、字符串内容损坏或不可预测的路径值。
- 不一致的 `prefix_` 和 `isAppModule_` 快照可能使模块注册使用错误名称或模块类型，导致缓存关联错误、模块加载失败或后续查询返回错误文件路径。
- 故障发生在共享模块管理器中，可能影响同一进程内其他 NativeEngine 和 worker 的模块加载。
- 尚无证据证明该竞态可以稳定实现受控内存破坏、跨应用模块替换、权限提升或任意代码执行。

## 触发条件

1. 同一进程中存在至少两个可并发运行的 NativeEngine，例如主引擎和 worker runtime。
2. 一个线程加载尚未缓存的 app native module，使 `LoadNativeModuleWithErrorInfo()` 更新 `prefix_` 和 `isAppModule_`。
3. 另一个线程在更新窗口内首次调用 `node_api_get_module_file_name()`；或者注册入口在没有继承 `mutex_` 的上下文中执行 `Register()`。
4. 两条执行路径对共享字段的读写发生重叠。实际触发频率取决于线程调度和模块加载时序。

## 修复建议

首选方案是删除全局的“当前加载模块”状态：将路径前缀和模块类型作为单次加载上下文传递，注册时使用线程局部加载上下文，文件名查询则使用与对应 `NativeEngine` 或模块缓存项绑定的不可变路径。这样可以同时避免数据竞争和不同引擎之间复用最后一次加载前缀的问题。

如果暂时保留现有字段，应增加专用状态锁，并在访问模块链表之前先取得一致快照。不要让 `Register()` 在持有 `nativeModuleListMutex_` 后再等待加载锁，否则动态库构造函数回调可能产生重入或锁顺序问题。

专用锁只能消除并发访问，不能解决全局字段保存“最后一次加载上下文”的设计问题，因此仍应迁移到每引擎、每模块或线程局部上下文。回归测试应同时启动两个 worker，加载不同前缀的 app module 并并发查询模块文件名；使用 ThreadSanitizer 检查共享字段访问，并验证每个引擎获得的模块名称、类型和路径均对应自身模块。

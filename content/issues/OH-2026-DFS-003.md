## 漏洞概述

`MetaFile::LoadChildren` 和 `CloudDiskMetaFile::LoadChildren` 都按 4096 字节的 `HmdfsDentryGroup` 枚举 dentry 元数据页。两个实现调用 `FileUtils::ReadFile` 后均不检查返回值，无论读取是否失败、是否到达 EOF 或是否只写入部分缓冲区，都会立即把该对象交给 `DecodeDentrys`。

`HmdfsDentryGroup` 在循环外以未显式初始化的栈对象声明，并在不同页之间重复使用。第一次读取失败时，未写入区域可能仍为未初始化数据；后续页读取失败或短读时，缓冲区还可能保留上一页的数据。解码器随后读取 bitmap、名称长度、名称和文件元数据，因此读取错误被错误地转换为正常的目录项结果，而 `LoadChildren` 最终仍返回成功。

两个实现均进入产品构建的 dentry 工具库。`CloudDiskMetaFile::LoadChildren` 还有明确的生产调用路径，可由云盘 FUSE 的目录枚举、删除空目录检查以及重命名冲突处理触发。当前仓库未发现普通 `MetaFile::LoadChildren` 的非测试调用点，因此该实现的实际可达性尚未确认。

当前 `master` 提交 `38dc2f94b310e6406792999cd7b0c308be74a6ef` 仍存在该问题。普通 `MetaFile` 实现由提交 `fee22b34210895a0592f4e7ec974ce409217b75b` 引入，云盘实现由提交 `d3f9e5a04dda13a17dfbf1850286350de805820b` 引入。普通实现已存在于 `OpenHarmony-v4.0-Beta1`；两个实现均已存在于 `OpenHarmony-v5.0-Beta1`，并延续到已逐文件核验的 `OpenHarmony-v6.0-Release`。未对其他发行分支作推断。

## 根本原因

### 两个 LoadChildren 实现忽略读取结果

**位置**: `utils/dentry/src/meta_file.cpp:644`

```cpp
int32_t MetaFile::LoadChildren(std::vector<MetaBase> &bases)
{
    // ...
    HmdfsDentryGroup dentryGroup;

    for (uint64_t i = 1; i < groupCnt + 1; i++) {
        uint64_t off = i * sizeof(HmdfsDentryGroup);
        FileUtils::ReadFile(fd_, off, sizeof(HmdfsDentryGroup), &dentryGroup);
        DecodeDentrys(dentryGroup, bases);
    }
    return E_OK;
}
```

**位置**: `utils/dentry/src/meta_file_clouddisk.cpp:709`

```cpp
int32_t CloudDiskMetaFile::LoadChildren(std::vector<MetaBase> &bases)
{
    // ...
    HmdfsDentryGroup dentryGroup;

    for (uint64_t i = 1; i < groupCnt + 1; i++) {
        uint64_t off = i * sizeof(HmdfsDentryGroup);
        ret = FileRangeLock::FilePosLock(fd_, off, DENTRYGROUP_SIZE, F_WRLCK);
        if (ret) {
            return ret;
        }
        FileUtils::ReadFile(fd_, off, sizeof(HmdfsDentryGroup), &dentryGroup);
        (void)FileRangeLock::FilePosLock(fd_, off, DENTRYGROUP_SIZE, F_UNLCK);
        DecodeDentrys(dentryGroup, bases);
    }
    return E_OK;
}
```

范围锁只约束协作方对相应文件区间的访问，并不能把失败或短读转换为完整页。这里既没有要求返回值等于 `sizeof(HmdfsDentryGroup)`，也没有在每轮读取前重新初始化缓冲区。

### ReadFile 明确允许失败和短读

**位置**: `utils/dentry/src/file_utils.cpp:28`

```cpp
int64_t FileUtils::ReadFile(int fd, off_t offset, size_t size, void *data)
{
    // ...
    off_t err = lseek(fd, offset, SEEK_SET);
    if (err < 0) {
        return -errno;
    }

    size_t readLen = 0;
    while (readLen < size) {
        ssize_t ret = read(fd, data, size - readLen);
        if (ret < 0) {
            return ret;
        } else if (ret == 0) {
            break;
        }
        readLen += static_cast<size_t>(ret);
    }
    return readLen;
}
```

该接口在 `lseek` 或 `read` 失败时返回负值，在 EOF 时返回实际读取长度。调用方必须确认返回值恰好等于目标结构大小。该循环还没有按 `readLen` 推进目标缓冲区地址；若底层通过多次短读凑够请求长度，后续读取会覆盖缓冲区开头，但函数仍可能返回完整长度。

### 解码器立即访问未完整写入的字段

**位置**: `utils/dentry/src/meta_file_clouddisk.cpp:687`

```cpp
for (uint32_t i = 0; i < DENTRY_PER_GROUP; i++) {
    int len = dentryGroup.nsl[i].namelen;
    if (!BitOps::TestBit(i, dentryGroup.bitmap) || len == 0 || len >= PATH_MAX) {
        continue;
    }

    std::string name(reinterpret_cast<const char *>(dentryGroup.fileName[i]), len);
    MetaBase base(name);
    base.mode = dentryGroup.nsl[i].mode;
    base.mtime = dentryGroup.nsl[i].mtime;
    base.size = dentryGroup.nsl[i].size;
    // ...
    bases.emplace_back(base);
}
```

普通 `MetaFile` 的解码器采用相同顺序。读取结果不完整时，bitmap 与 `namelen` 可能来自未写入字节、部分新数据或上一页残留数据。现有检查只限制 `namelen < PATH_MAX`，没有证明对应名称字节已由本次读取完整写入。

## 影响

- 目录枚举可能返回上一页重复项、伪造项、错误名称或错误的 mode、size、mtime、cloudId 等元数据。
- 云盘 FUSE 的 `readdir` 可能向调用方返回错误目录内容；删除目录检查可能把非空目录判断为空，或把空目录判断为非空；重命名冲突处理也可能依据错误名称作出决定。
- 若未完整写入的数据组合出有效 bitmap 和异常 `namelen`，`std::string` 会按该长度读取名称区域，可能造成越界读取、异常内存访问或进程崩溃。该结果仅由源码路径推导，尚未动态复现。
- OpenHarmony 标准系统的默认构建配置会把普通未初始化局部变量置零，这会降低第一次完整读取失败时直接使用随机栈数据的风险，但不能消除跨循环复用的上一页残留数据，也不能修复部分覆盖或错误返回成功的问题。

当前证据尚未证明普通应用可以直接修改 dentry cache 文件或稳定制造底层 I/O 失败，因此不支持权限提升、稳定信息泄露或远程利用结论。

## 触发条件

1. `LoadChildren` 的 `fstat` 成功，并根据当时的文件大小计算出至少一个 dentry 元数据页。
2. 随后的页读取发生 `lseek`/`read` 错误、在 EOF 前只返回部分数据，或文件在 `fstat` 后被并发截短。
3. 两个实现忽略 `ReadFile` 的实际返回值，并继续调用 `DecodeDentrys`。
4. 未完整写入的缓冲区中存在可通过 bitmap 和 `namelen` 检查的数据，或旧页数据被再次解释为当前页。

静态文件末尾单独存在不足 4096 字节的残页时，`GetDentryGroupCnt` 的整除计算通常不会枚举该残页；主要风险来自 `fstat` 后的状态变化和实际 I/O 失败。`CloudDiskMetaFile` 路径可由正常云盘 FUSE 操作到达，但尚未确认非特权调用者能够稳定控制上述读取失败条件。

## 修复建议

建议在每次循环内重新值初始化 `HmdfsDentryGroup`，保存 `ReadFile` 返回值，并且仅在读取长度严格等于结构大小时调用 `DecodeDentrys`。读取失败或短读应释放已获取的范围锁，记录错误并向调用方返回 `EIO` 等明确错误，不能继续返回 `E_OK`。

```cpp
for (uint64_t i = 1; i < groupCnt + 1; ++i) {
    HmdfsDentryGroup dentryGroup{};
    uint64_t off = i * sizeof(dentryGroup);
    int64_t readSize = FileUtils::ReadFile(fd_, off, sizeof(dentryGroup), &dentryGroup);
    if (readSize != static_cast<int64_t>(sizeof(dentryGroup))) {
        return EIO;
    }
    DecodeDentrys(dentryGroup, bases);
}
```

云盘实现需要保证所有错误分支都释放范围锁，建议使用作用域守卫或 RAII 管理锁。还应修正 `FileUtils::ReadFile` 的重试写入位置，使每轮 `read` 写入 `static_cast<uint8_t *>(data) + readLen`，避免多次短读覆盖缓冲区开头。解码阶段可进一步校验名称需要的 slot 数量和剩余缓冲区范围，避免损坏元数据把 `namelen` 扩大为越界访问。

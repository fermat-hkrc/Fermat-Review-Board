## 漏洞概述

`FormRendererDispatcherImpl::OnNotifyDumpInfo()` 将调用方提供的 `std::vector<std::string>& info` 按引用捕获到异步任务中。调用线程最多等待 65 毫秒；超时后调用 `RemoveTask()` 并立即返回。但是，`RemoveTask()` 只能删除仍在事件队列中的任务，不能等待已经出队或正在执行的回调结束。

存在一个竞态窗口：事件线程可以先将任务从队列取出，随后阻塞在 `dumpCondition->mtx`；调用线程等待 65 毫秒后重新取得同一互斥锁，向 `info` 添加超时信息并尝试删除任务。此时任务已经不在队列中，删除操作无效。调用函数返回并销毁上层的局部 `info` 后，事件线程取得锁并执行 `uiContent->DumpInfo(params, info)`，继续使用悬空引用。

该窗口由源码的锁和任务队列语义确立。当前未动态复现崩溃，因此只确认潜在的释放后使用、内存破坏和 FormRenderer 进程崩溃风险，不声明稳定利用或代码执行。

仅确认当前 master commit `533810af82fc7314e6fc5c55a9ef5917b076654e` 受影响。未确认对应的公开发布版本或已修复版本。

## 根本原因

**位置**: `interfaces/inner_api/form_render/src/form_renderer_dispatcher_impl.cpp:343`

调用线程在投递任务前持有 `dumpCondition->mtx`。异步任务捕获 `&info`，并在开始执行时获取同一个互斥锁：

```cpp
std::shared_ptr<DumpInfoCondition> dumpCondition = std::make_shared<DumpInfoCondition>();
std::unique_lock<std::mutex> lock(dumpCondition->mtx);
handler->PostTask(
    [content = uiContent_, params, &info, dumpCondition]() {
        std::unique_lock<std::mutex> lock(dumpCondition->mtx);
        auto uiContent = content.lock();
        if (!uiContent) {
            dumpCondition->cv.notify_all();
            return;
        }
        uiContent->DumpInfo(params, info);
        dumpCondition->cv.notify_all();
    },
    "OnNotifyDumpInfoTask");
```

如果事件线程已经从队列取出任务，但尚未获得 `dumpCondition->mtx`，任务不再是待删除事件，却仍然尚未使用 `info`。

超时分支没有检查取消是否成功，也没有等待任务退出：

```cpp
if (dumpCondition->cv.wait_for(lock, std::chrono::milliseconds(DUMP_WAIT_TIME)) == std::cv_status::timeout) {
    info.push_back("dump timeout " + std::to_string(DUMP_WAIT_TIME) + "ms");
    handler->RemoveTask("OnNotifyDumpInfoTask");
}
```

`wait_for()` 超时返回时，调用线程已经重新持有 `dumpCondition->mtx`。这会暂时阻止任务进入 `DumpInfo()`，但不能延长 `info` 的生命周期。`OnNotifyDumpInfo()` 离开作用域时释放锁并返回，任务随后可以取得锁并使用 `&info`。

**位置**: `interfaces/inner_api/form_render/src/form_renderer_dispatcher_stub.cpp:190`

IPC Stub 中的 `info` 是请求处理函数的局部变量：

```cpp
std::vector<std::string> info;
OnNotifyDumpInfo(params, info);
if (!reply.WriteStringVector(info)) {
    return ERR_INVALID_VALUE;
}
```

当 `HandleOnNotifyDumpInfo()` 返回后，这个向量被析构。异步任务若随后调用 `DumpInfo(params, info)`，会对已经结束生命周期的对象执行读写。

在 EventHandler 的基础事件队列实现中，事件被执行前会先从队列移除；`RemoveTask(name)` 只对队列中仍存在的同名任务执行删除。在 FFRT 事件队列实现中，按名称取消失败时也明确表示任务可能已经执行。因此，超时后的 `RemoveTask()` 不是等待或同步屏障，不能保证 lambda 不再运行。

## 影响

- 异步 dump 回调可能对已经析构的 `std::vector<std::string>` 执行读写，产生释放后使用。
- 根据失效向量及其底层存储被复用的情况，可能造成 FormRenderer 进程崩溃或内存破坏。
- dump 请求可能收到超时结果，而已超时任务仍在后台执行，形成后续请求难以预测的状态。

当前没有动态运行结果证明稳定崩溃、可控内存破坏或任意代码执行。风险取决于事件任务恰好在超时前出队、锁调度顺序以及 `info` 返回后的内存复用情况。

## 触发条件

1. 已建立的 FormRenderer IPC 调用方发起 `NOTIFY_DUMP_INFO` 请求。
2. `OnNotifyDumpInfoTask` 在 65 毫秒超时前从 EventHandler 队列出队。
3. 事件线程在 `dumpCondition->mtx` 上等待，或者直到调用线程处理超时分支后才获得该锁。
4. 调用线程超时，执行 `RemoveTask()` 并从 `OnNotifyDumpInfo()` 返回。
5. IPC Stub 的局部 `info` 生命周期结束后，事件线程继续调用 `UIContent::DumpInfo()`。

该问题不要求多个线程同时无锁修改 `info`；互斥锁串行化了访问，但没有保证引用对象在异步任务完成前仍然存活。是否能够由普通第三方应用直接发起该内部 IPC 请求尚未确认，因此不声明无权限远程触发。

## 修复建议

不要在可超时的异步任务中捕获调用方局部对象的引用。将结果和完成状态放入任务与等待方共同持有的堆对象，并让任务只写该对象。等待方仅在确认任务已完成后将结果移动到 `info`；超时后直接返回，后台任务即使继续执行也不会访问调用方栈对象。

```diff
 struct DumpInfoCondition {
     std::mutex mtx;
     std::condition_variable cv;
+    std::vector<std::string> result;
+    bool done = false;
 };

-[content = uiContent_, params, &info, dumpCondition]() {
+[content = uiContent_, params, dumpCondition]() {
     std::unique_lock<std::mutex> lock(dumpCondition->mtx);
     auto uiContent = content.lock();
     if (uiContent) {
-        uiContent->DumpInfo(params, info);
+        uiContent->DumpInfo(params, dumpCondition->result);
     }
+    dumpCondition->done = true;
     dumpCondition->cv.notify_all();
 }

-if (dumpCondition->cv.wait_for(lock, timeout) == std::cv_status::timeout) {
+if (!dumpCondition->cv.wait_for(lock, timeout, [&] { return dumpCondition->done; })) {
     info.push_back("dump timeout ...");
     handler->RemoveTask("OnNotifyDumpInfoTask");
+    return;
 }
+info = std::move(dumpCondition->result);
```

还应检查 `PostTask()` 的返回值。若投递失败，应立即返回错误，不能进入没有任务会通知的等待流程。

建议增加以下回归测试：

- 任务仍在队列中时超时，确认取消后不会执行。
- 任务已经出队但阻塞在 `dumpCondition->mtx` 时超时，确认调用方返回后任务不会访问其 `info`。
- `UIContent::DumpInfo()` 正常完成时，结果仅在完成状态为真后复制或移动给调用方。
- `uiContent_` 失效和 `PostTask()` 失败时，等待方能立即得到明确错误。
- 使用 AddressSanitizer 对“已出队后超时”时序执行回归测试。

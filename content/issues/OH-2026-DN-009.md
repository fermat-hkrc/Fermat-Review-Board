## 漏洞概述

通知订阅扩展加载器在 `dlopen` 和 `dlsym` 成功后返回动态库创建的 `NotificationSubscriberExtension*`，但没有把 handle 保存到对象或统一模块缓存。每次成功创建都会增加动态库引用计数，后续没有对应释放位置。

## 根本原因

**位置**：`frameworks/js/napi/src/extension/loader/notification_subscriber_extension_module_loader.cpp`

```cpp
void *handle = dlopen(modulePath.c_str(), RTLD_NOW);
auto create = reinterpret_cast<CreateExtensionFunc>(dlsym(handle, symbol));
auto *extension = create();
return extension; // handle 生命周期与实例脱离
```

失败分支会执行 `dlclose`。成功后又不能立即关闭，因为扩展实例的代码和 vtable 仍位于该动态库中。

## 影响

- 重复创建 notification subscriber extension 会累积动态加载引用。
- 资源保留发生在承载通知扩展的应用进程。
- 长期反复创建会增加进程资源占用，并使动态库无法按实例生命周期卸载。

## 触发条件

Ability 框架在同一宿主进程中多次成功创建并销毁 STS notification subscriber extension。

## 修复建议

为动态库建立引用计数所有者，使扩展实例或模块缓存持有 handle，并在最后一个实例销毁后执行 `dlclose`。不得在仍存在实例时卸载动态库。

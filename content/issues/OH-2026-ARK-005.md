## Executive Summary

能够控制序列化 StyledString 字节的攻击方 Mallory 可以省略嵌套结构的专用结束标签，使 ArkUI 的 SpanString TLV 解码任务在输入末尾持续循环。`StyledString.unmarshalling(ArrayBuffer)` 直接接受调用方提供的字节；启用系统剪贴板支持时，ArkUI 还会自动解码 `openharmony.styled-string` 自定义记录。该问题不绕过身份验证，也不造成内存破坏；已由源码确认的最小影响是单次解码无法返回并持续占用执行线程和 CPU。

我核对了提交 `d8847980b8c1fdbb6e79b5a9b641cabde4ba9a70` 的入口、完整解码链、7 个同根因循环和相关 Git 历史。没有运行会故意制造无限循环的触发输入，因此本报告不声称已经动态复现。当前仓库历史没有把这些提交映射到可核验的公开发行标签，故受影响版本仅标记为本次检查的提交；首个受影响发行版和已修复发行版尚未确认。

## Background

SpanString 使用自定义 TLV 格式保存文本、普通 Span、ImageSpan 以及嵌套样式。顶层结构以通用 `TLV_END`（`0x00`）结束；多个嵌套结构则使用各自的非零结束标签。解码器应在看到对应结束标签时正常完成，并在输入提前结束时返回解析错误。

`TLVUtil::ReadUint8` 在仍有数据时读取一个字节并推进 `cursor`。到达 EOF 后，它返回与顶层结束标记相同的 `0x00`，但不推进 `cursor`：

**位置：** `frameworks/core/components_ng/pattern/text/span/tlv_util.h`，`TLVUtil::ReadUint8`

```cpp
static uint8_t ReadUint8(std::vector<uint8_t>& buff, int32_t& cursor)
{
    if (static_cast<size_t>(cursor + 1) > buff.size()) {
        return TLV_END;
    }
    return buff[cursor++];
}
```

这个行为能让等待 `0x00` 的顶层循环在 EOF 时退出，却无法为等待其他结束标签的嵌套循环表达“输入已结束”。

## Vulnerability Details

### 专用结束标签循环不接受 EOF

以下 7 个循环都用 `ReadUint8` 读取下一标签，只把各自的专用结束标签作为退出条件。它们没有检查 EOF，也没有验证每次迭代后游标是否推进。

| 解码函数 | 等待的结束标签 | 从 SpanString 到达该函数的结构 |
| --- | --- | --- |
| `SpanItem::DecodeTlv` | `TLV_SPANITEM_END_TAG` (`0x51`) | 普通 SpanItem |
| `ImageSpanItem::DecodeTlv` | `TLV_SPANITEM_END_TAG` (`0x51`) | ImageSpanItem |
| `TLVUtil::ReadImageSpanAttribute` | `TLV_IMAGESPANATTRIBUTE_END_TAG` (`0x41`) | ImageSpanItem 的 imageAttribute |
| `TLVUtil::ReadImageSpanSize` | `TLV_IMAGESPANSIZE_END_TAG` (`0x45`) | imageAttribute 的 size |
| `TLVUtil::ReadPaddingProperty` | `TLV_PADDINGPROPERTY_END_TAG` (`0x4B`) | imageAttribute 的 margin 或 padding |
| `TLVUtil::ReadRadialGradient` | `TLV_SPAN_TEXT_LINE_STYLE_RADIALGRADIENT_END_TAG` (`0xB2`) | 普通 SpanItem 的 radialGradient |
| `TLVUtil::ReadLinearGradient` | `TLV_SPAN_TEXT_LINE_STYLE_LINEARGRADIENT_END_TAG` (`0xB8`) | 普通 SpanItem 的 linearGradient |

例如，普通 SpanItem 的循环只识别 `0x51`：

**位置：** `frameworks/core/components_ng/pattern/text/span_node.cpp`，`SpanItem::DecodeTlv`

```cpp
for (uint8_t tag = TLVUtil::ReadUint8(buff, cursor);
    tag != TLV_SPANITEM_END_TAG; tag = TLVUtil::ReadUint8(buff, cursor)) {
}
```

渐变、图片尺寸、边距和图片属性的循环具有相同控制结构。以 LinearGradient 为例，输入在 `TLV_SPAN_TEXT_LINE_STYLE_LINEARGRADIENT_BEGIN_TAG` 后结束时，第一次循环读取就得到 `0x00`；`default` 不改变游标，更新表达式再次在同一 EOF 位置得到 `0x00`：

**位置：** `frameworks/core/components_ng/pattern/text/span/tlv_util.cpp`，`TLVUtil::ReadLinearGradient`

```cpp
for (uint8_t tag = TLVUtil::ReadUint8(buff, cursor);
    tag != TLV_SPAN_TEXT_LINE_STYLE_LINEARGRADIENT_END_TAG; tag = TLVUtil::ReadUint8(buff, cursor)) {
    switch (tag) {
        case TLV_SPAN_TEXT_LINE_STYLE_LINEARGRADIENT_DIRECTION: {
            direction = ReadInt32(buff, cursor);
            break;
        }
        case TLV_SPAN_TEXT_LINE_STYLE_LINEARGRADIENT_ANGLE: {
            angle = ReadDimension(buff, cursor);
            break;
        }
        default:
            break;
    }
}
```

这不局限于 LinearGradient。每个表中函数都可以通过其正常父标签单独到达，然后在自己的结束标签前截断。`ReadImageSpanSize` 和 `ReadPaddingProperty` 是 `ReadImageSpanAttribute` 的嵌套变体，但不依赖先触发外层循环：父标签会直接调用相应子解析器，子解析器随即停在自己的 EOF 循环中。

### 调用方控制的 ArrayBuffer 进入相同解码链

`JSSpanString::Unmarshalling` 只检查第一个参数是否为 `ArrayBuffer`，随后复制全部字节。异步工作函数把该向量直接传给 `SpanString::DecodeTlv`：

**位置：** `frameworks/bridge/declarative_frontend/style_string/js_span_string.cpp`，`JSSpanString::Unmarshalling` 与 `UnmarshallingExec`

```cpp
size_t bufferSize = static_cast<size_t>(arrayBuffer->ByteLength());
void* buffer = arrayBuffer->GetBuffer();
std::vector<uint8_t> buff(
    static_cast<uint8_t*>(buffer), static_cast<uint8_t*>(buffer) + bufferSize);
asyncContext->buffer = buff;
```

```cpp
asyncContext->spanString = SpanString::DecodeTlv(asyncContext->buffer, std::move(unmarshallCallback),
    asyncContext->instanceId);
```

`SpanString::DecodeTlvExt` 先进入 `DecodeTlvOldExt`。当顶层数据声明 Span 列表时，`DecodeSpanItemListExt` 根据调用方提供的 Span 类型调用 `SpanItem::DecodeTlv` 或 `ImageSpanItem::DecodeTlv`。因此，普通 Span 与 ImageSpan 的外层循环都可直接到达；普通 Span 的样式标签继续到达两个渐变循环，ImageSpan 的属性标签继续到达图片属性、尺寸和边距循环。

### 剪贴板自定义记录也会被直接解析

启用 `SYSTEM_CLIPBOARD_SUPPORTED` 时，同步和异步读取路径都会取得 `openharmony.styled-string` 对应的字节数组并调用相同解码函数：

**位置：** `adapter/ohos/capability/clipboard/clipboard_impl.cpp`，`ClipboardImpl::GetDataSync` 与 `ProcessPasteDataRecord`

```cpp
auto itemData = customData->GetItemData();
if (itemData.find(SPAN_STRING_TAG) == itemData.end()) {
    continue;
}
auto spanStr = SpanString::DecodeTlv(itemData[SPAN_STRING_TAG]);
```

异步路径会优先使用普通文本和 HTML；要从该路径到达 TLV 解码，自定义记录必须没有先被这些表示处理。同步文本读取路径在该段代码中先检查自定义数据。源码能够确认这些字节会进入解码器，但本次检查没有验证系统剪贴板对跨应用写入该自定义类型的权限规则，因此不能据此断言任意应用都能攻击其他应用。

### 引入历史和发行范围

Git 历史显示，提交 `8f5412ed358e` 在 2024 年 5 月 23 日加入 TLV 解码器、`ReadUint8` 以及 SpanItem、ImageSpanItem、图片属性、图片尺寸和边距的专用结束标签循环。剪贴板解码入口随后由 `6850b57483d5` 在 2024 年 5 月 29 日加入，JavaScript unmarshalling 入口由 `575acd9aa0b9` 在 2024 年 8 月 13 日加入。提交 `6fd401794e48` 在 2026 年 5 月 13 日沿用同一循环模式加入 RadialGradient 和 LinearGradient 解码。

这些提交在当前 `master` 仍存在。仓库可见的发行标签早于上述引入提交，且没有可供检查的维护分支或修复提交，所以不能从现有历史可靠确定首个受影响发行版、受影响发行范围或首个修复发行版。

## Exploitability Analysis

源码确认的基本能力是让一个解码调用永不返回。对于 `StyledString.unmarshalling`，循环发生在 N-API 异步工作任务中；Promise 无法完成，该工作线程持续消耗 CPU。对于剪贴板同步读取，解码发生在同步任务内部，任务和等待它的调用路径都无法完成；异步剪贴板路径则会占住对应后台任务。多次提交畸形输入可能占用更多执行资源，但本次没有测量线程池大小、调度行为或进程级影响。

攻击条件取决于入口：

- JavaScript 入口要求目标应用把 Mallory 可控的字节传给 `StyledString.unmarshalling`。仅由应用自己构造畸形数据时，影响局限于该应用自身。
- 剪贴板入口要求目标设备启用系统剪贴板支持，目标应用读取 StyledString 自定义记录，并且 Mallory 能通过系统许可的方式控制该记录。跨应用写入权限尚未验证。
- 输入必须先构造出相应父结构，并在某个专用结束标签前结束。单纯缺少顶层 `TLV_END` 不会触发该循环，因为顶层把 EOF 返回的 `0x00` 当作正常终止。

现有源码不支持把影响提升为内存破坏、信息泄露或代码执行。部分同一解析器中的定长读取还存在独立的边界检查问题，但它们不是本报告所述无限循环成立的前提，也不应与本根因合并评估影响。

## Remediation

不要再用 `TLV_END` 同时表示实际字节 `0x00` 和读取失败。建议把底层读取接口改为显式返回成功状态，例如 `bool ReadUint8(..., uint8_t& value)` 或 `std::optional<uint8_t>`。所有 7 个专用结束标签循环必须在 EOF 时立即返回解析错误，并把失败状态一直传递到 `SpanString::DecodeTlv` 及外部 API；外部 API 不应返回部分解析对象。

只在 LinearGradient 循环中加入 `tag == TLV_END` 判断会遗漏另外 6 个可达循环。若为兼容现有格式而保留 `0x00` 顶层结束标签，解析器仍应依据“是否成功读取字节”区分真实 `0x00` 与 EOF，而不是仅检查标签值。

回归测试至少应覆盖：

- 完整的普通 Span、ImageSpan、图片属性、图片尺寸、margin、padding、RadialGradient 和 LinearGradient 数据；
- 每个专用开始标签或父标签后立即 EOF；
- 每个结构解析一个合法字段后 EOF；
- 专用结构中出现实际 `0x00`、随后仍缺少专用结束标签；
- JavaScript unmarshalling 和剪贴板两条真实入口收到解析错误并及时返回；
- 完整合法 TLV 的既有序列化兼容性。

## Summary

当前提交的 SpanString TLV 解码器有 7 个同根因的专用结束标签循环。它们在输入截断时反复读取不会推进游标的 EOF，并使解码任务持续运行。调用方提供的 `ArrayBuffer` 可直接到达这些循环；系统剪贴板的 StyledString 自定义记录也进入相同解码器，但跨应用控制该记录的权限尚未验证。修复必须让所有嵌套解析器显式识别并传播 EOF，而不是只修补最初发现的 LinearGradient 循环。

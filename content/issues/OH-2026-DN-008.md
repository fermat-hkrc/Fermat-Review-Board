## 漏洞概述

PC 通知授权对话框在每个页面实例的 `aboutToAppear` 中调用 `display.on('foldStatusChange', callback)`。该回调闭包捕获当前组件实例，但页面退出、按钮操作结束以及 UI Extension 会话终止路径都没有调用对应的 `display.off`。

Display 的原生实现会为传入回调创建强引用，把回调引用和原生监听器保存在映射中；只有 `off` 路径会删除该映射项并向显示服务注销监听器。因此，在同一进程内反复创建和结束 PC 对话框会保留已经结束会话的回调及其捕获状态，后续折叠状态变化还可能调用旧回调。

PC 页面进入 `enable_notification_dialog_hap` 的 ArkTS 构建，并由组件 `service_group` 纳入产品。当前 `master` 提交 `c76a751c286e4e3fc614b4fccd57dfbfa13d2aa3` 仍存在问题。注册代码由提交 `b9994b8157804c7fddb4103d62e4e53ae445ddf0` 引入；仓库现有公开标签不包含该提交，因此这里只确认当前精确提交，不推断具体发行版本。

本次没有通过运行时循环创建会话测量监听器数量或内存变化。尚未确认普通应用能够无限制触发 PC 系统对话框会话。

## 根本原因

### 页面出现时创建匿名局部回调并注册

**位置**: `services/dialog_ui/enable_notification_dialog/entry/src/main/ets/pages/pcNotificationDialog.ets:269`

```typescript
async aboutToAppear(): Promise<void> {
  this.dialog = storage.get('dialog') as EnableNotificationDialog;
  this.session = storage.get('session') as UIExtensionContentSession;
  this.updateAvoidWindow();
  this.registerFoldStatusChange();
  try {
    await this.updateStatus();
  } catch (err) {
    // ...
  }
}
```

`registerFoldStatusChange` 在局部变量中创建捕获 `this` 的回调，并将其注册到全局 Display 事件源：

```typescript
async registerFoldStatusChange(): Promise<void> {
  let callback: Callback<display.FoldStatus> = async (data: display.FoldStatus) => {
    try {
      let dis = DisplayUtils.getCurWindowDisplay(this.dialog?.subWindow);
      // ...
      this.updateContentCompoment();
    } catch (err) {
      // ...
    }
  };
  try {
    display.on('foldStatusChange', callback);
  } catch (err) {
    // ...
  }
}
```

回调没有保存为类成员，后续也无法使用相同函数对象执行精确注销。

### 所有会话结束路径都遗漏 off

**位置**: `services/dialog_ui/enable_notification_dialog/entry/src/main/ets/pages/pcNotificationDialog.ets:283`

```typescript
async aboutToDisappear(): Promise<void> {
  console.info(TAG, `aboutToDisappear`);
  this.session?.terminateSelf();
}
```

用户点击按钮时，`enableNotification` 会销毁子窗口并终止会话；该路径同样没有注销监听器。仓库当前代码中没有针对 `foldStatusChange` 的 `display.off` 调用。

Display 原生实现会通过 `napi_create_reference` 创建回调强引用，并把它放入 `jsCbMap_[type]`。其注销实现只有在 `off` 调用时才移除回调、注销 `IFoldStatusListener` 并删除映射项。页面自身结束不会自动经过这条清理路径。

## 影响

- 同一进程内反复创建 PC 通知授权对话框时，Display 回调引用、原生监听器以及闭包捕获的页面和会话状态可能持续累积。
- 折叠状态变化可能继续触发已结束会话的旧回调，产生重复布局工作和针对已销毁窗口的失败调用。
- 资源会在承载进程或相关运行时整体结束时释放，因此这不是跨进程永久泄漏；实际增长取决于进程内会话创建次数。

当前证据不支持权限提升、敏感信息泄露或稳定系统拒绝服务结论。外部调用者对对话框创建频率和会话数量的控制能力尚未确认。

## 触发条件

1. 设备配置选择 PC 通知授权页面。
2. 页面实例进入 `aboutToAppear`，成功注册 `foldStatusChange` 回调。
3. 页面随后通过 `aboutToDisappear`、按钮处理或异常路径结束会话。
4. 承载进程继续运行，且代码没有调用 `display.off` 清理该实例的回调。
5. 重复创建会话会增加保留项；后续折叠状态变化会使旧监听器参与回调。

源码能够确认单次注册缺少对应清理。资源累计规模和可稳定触发次数没有动态验证。

## 修复建议

建议把折叠状态回调保存为稳定的类成员，并对注册状态进行幂等管理：

```typescript
private foldStatusCallback?: Callback<display.FoldStatus>;
private foldStatusRegistered: boolean = false;

private unregisterFoldStatusChange(): void {
  if (!this.foldStatusRegistered || this.foldStatusCallback === undefined) {
    return;
  }
  display.off('foldStatusChange', this.foldStatusCallback);
  this.foldStatusRegistered = false;
  this.foldStatusCallback = undefined;
}
```

注册时应复用这个成员函数对象，避免重复注册。`aboutToDisappear` 应调用统一清理函数；按钮完成、异常销毁和其他可能绕过正常生命周期的会话终止路径也应调用同一函数。清理函数需要处理重复调用和 `off` 抛出的异常，确保窗口与会话清理仍能继续执行。

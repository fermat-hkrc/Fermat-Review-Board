## 漏洞概述

`__self_init()` 使用经典的双重检查锁定模式(DCLP)保护 `addr2ent` 哈希表的初始化，但实现存在两个缺陷：(1) 外层检查 `io_init` 无内存屏障，在 ARM 弱内存序下线程可能观察到 `io_init=true` 但 `addr2ent` 尚未完全初始化的状态；(2) `io_init` 在锁内初始化完成后未被设置为 `true`（或设置语句在 `pthread_mutex_unlock` 之后），导致多线程可重复进入初始化路径。

## 根本原因

**位置**: `libohtee/drv_io_share.c:33`

```c
static struct htable addr2ent;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static bool io_init;

static void __self_init(void)
{
    if (io_init) {        // ← 无 acquire 屏障的读取
        return;
    }
    pthread_mutex_lock(&lock);
    if (!io_init) {
        init_htable(&addr2ent, HTABLE_SIZE);
        // io_init = true;  ← 即使在此处设置，外层读取仍无 acquire 语义
    }
    pthread_mutex_unlock(&lock);
}
```

**问题**:
1. ARM 弱内存序下，`io_init` 的 store 可能被 CPU 重排序到 `init_htable` 的 store 之前，外层线程看到 `io_init=true` 时哈希表可能未完全写入
2. 若 `io_init` 未在临界区内正确设置（代码可见部分未见赋值），则每次调用都会进入锁内重新初始化，在并发下产生 double-init 竞态

## 影响

- **数据损坏**：并发初始化哈希表导致内存结构不一致
- **Use-After-Init**：线程观察到部分初始化的哈希表，后续 `__get_entry` 访问非法内存
- **TEE 驱动崩溃**：IO 共享内存映射表损坏可导致 TEE 内核异常

## 触发条件

1. 多个 TA 或驱动线程同时首次调用 IO 共享内存映射接口
2. 两个线程几乎同时到达 `__self_init()`
3. 在 ARM 处理器上（OpenHarmony 主要运行平台），弱内存序使竞态窗口显著增大
4. 初始化竞争成功后，后续的 `htable_get_bucket` 访问损坏的哈希表结构

## 修复建议

使用 `pthread_once` 或带 acquire/release 语义的原子操作：

```c
#include <stdatomic.h>

static atomic_bool io_init = false;

static void __self_init(void)
{
    if (atomic_load_explicit(&io_init, memory_order_acquire)) {
        return;
    }
    pthread_mutex_lock(&lock);
    if (!atomic_load_explicit(&io_init, memory_order_relaxed)) {
        init_htable(&addr2ent, HTABLE_SIZE);
        atomic_store_explicit(&io_init, true, memory_order_release);
    }
    pthread_mutex_unlock(&lock);
}
```

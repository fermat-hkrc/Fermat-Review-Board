## 漏洞概述

`BundleUtil::DeleteJsonFile` 在 LiteOS-M 分支（`#else`）中先调用 `IsFile()` 检查文件是否存在，再调用 `unlink()` 删除。检查与使用之间存在竞争窗口，攻击者可通过符号链接替换使 `unlink` 删除非预期文件。标准系统分支通过 `BundleDaemonClient` 保护，但 LiteOS-M 分支无此保护。

## 根本原因

**位置**: `services/bundlemgr_lite/src/bundle_util.cpp:302`

```cpp
void BundleUtil::DeleteJsonFile(const char *bundleTmpJsonPath)
{
    if (IsFile(bundleTmpJsonPath)) {       // CHECK: 验证是否为普通文件
#ifdef OHOS_APPEXECFWK_BMS_BUNDLEMANAGER
        // 标准系统：通过 BundleDaemonClient 的 realpath+白名单保护
        BundleDaemonClient::GetInstance().RemoveFile(bundleTmpJsonPath);
#else
        // LiteOS-M：无任何保护，直接 unlink
        (void)unlink(bundleTmpJsonPath);   // USE: 竞争窗口内可被替换为 symlink
#endif
    }
}
```

**问题**:
1. `IsFile()` 检查与 `unlink()` 操作之间存在时间窗口
2. 攻击者可在窗口内将目标路径替换为指向关键文件的符号链接
3. LiteOS-M 分支缺失标准系统的 `realpath` + 白名单校验

## 影响

- 在 LiteOS-M 平台上可删除任意文件
- 可删除系统配置文件造成服务异常
- 可删除其他应用数据

## 触发条件

1. 目标运行于 LiteOS-M 平台（无 `OHOS_APPEXECFWK_BMS_BUNDLEMANAGER` 宏）
2. 攻击者对 `bundleTmpJsonPath` 所在目录有写权限
3. 在 `IsFile()` 返回 true 之后、`unlink()` 执行之前的窗口内
4. 将 `bundleTmpJsonPath` 替换为指向目标文件的符号链接
5. `unlink()` 删除符号链接指向的文件

## 修复建议

```cpp
void BundleUtil::DeleteJsonFile(const char *bundleTmpJsonPath)
{
-   if (IsFile(bundleTmpJsonPath)) {
#ifdef OHOS_APPEXECFWK_BMS_BUNDLEMANAGER
+   if (IsFile(bundleTmpJsonPath)) {
        BundleDaemonClient::GetInstance().RemoveFile(bundleTmpJsonPath);
+   }
#else
+   // 使用 O_NOFOLLOW 打开验证非符号链接，再通过 fd 操作
+   int fd = open(bundleTmpJsonPath, O_RDONLY | O_NOFOLLOW);
+   if (fd < 0) {
+       return;
+   }
+   struct stat st;
+   if (fstat(fd, &st) == 0 && S_ISREG(st.st_mode)) {
+       unlink(bundleTmpJsonPath);
+   }
+   close(fd);
#endif
-   }
}
```

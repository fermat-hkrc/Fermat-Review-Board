## 漏洞概述

PC 通知授权对话框通过 `DisplayUtils.getCurWindowDisplay` 获取子窗口所在的 `Display`。该辅助函数的返回类型明确包含 `undefined`，并在显示 ID 缺失或查询抛出异常时返回 `undefined`。`pcNotificationDialog.ets` 中的两个调用位置没有检查返回值，随后直接读取 `width` 或 `height`。

本报告合并 2 条有效报告，分别对应 `moveToDisplayCenter` 中的 `display.width`/`display.height` 访问，以及折叠状态回调中的 `dis.height` 访问。两个位置外围都有 `try/catch`，因此当前证据表明异常会中断本次定位或布局更新，而不是作为未处理异常继续传播。

该页面进入 `enable_notification_dialog_hap` 的 ArkTS 资源构建，并由组件的 `service_group` 纳入产品。当前 `master` 提交 `c76a751c286e4e3fc614b4fccd57dfbfa13d2aa3` 仍存在问题。辅助函数已存在于 `OpenHarmony-v6.0-Release`，但两个当前直接解引用位置由后续提交引入；仓库现有公开标签中没有包含完整问题状态的标签，因此这里只确认当前精确提交，不推断具体发行版本。

本次没有执行显示服务故障注入或动态复现。尚未确认普通应用能够稳定使子窗口显示查询在这两个位置失败。

## 根本原因

### 辅助函数允许返回 undefined

**位置**: `services/dialog_ui/enable_notification_dialog/entry/src/main/ets/common/displayUtils.ets:27`

```typescript
public static getCurWindowDisplay(win: window.Window): display.Display | undefined {
  try {
    let displayId: number | undefined = win.getWindowProperties().displayId;
    if (displayId !== undefined) {
      let currentDisplay = display.getDisplayByIdSync(displayId);
      return currentDisplay;
    }
    return undefined;
  } catch (err) {
    console.error(Constants.TAG, `getCurWindowDisplay failed, code=${err?.code}, msg=${err?.message}.`);
    return undefined;
  }
}
```

调用方必须把返回值视为可选值。类型断言或外围异常捕获不能代替读取属性前的显式检查。

### 居中定位路径直接读取 width 和 height

**位置**: `services/dialog_ui/enable_notification_dialog/entry/src/main/ets/pages/pcNotificationDialog.ets:408`

```typescript
async moveToDisplayCenter(): Promise<void> {
  try {
    // ...
    let display = DisplayUtils.getCurWindowDisplay(this.dialog?.subWindow);
    this.dialog?.subWindow?.resize(this.contentComW, this.contentComH);
    this.dialog?.subWindow?.moveWindowTo((display.width - this.contentComW) / 2,
       (display.height - this.contentComH) / 2);
  } catch (err) {
    console.error(TAG, `moveToDisplayCenter fail. code=${err?.code} msg=${err?.message}`);
  }
}
```

`updateContentCompoment` 会先查询一次 `Display`，并通过 `shouldMoveToDisplayCenter` 检查该值。只有第一次查询有效并判定需要居中时才会进入 `moveToDisplayCenter`。但该方法在若干异步窗口操作之后再次独立查询显示对象；第二次查询失败或窗口状态在期间变化时，仍会在读取属性处抛出异常。

### 折叠状态回调直接读取 height

**位置**: `services/dialog_ui/enable_notification_dialog/entry/src/main/ets/pages/pcNotificationDialog.ets:438`

```typescript
let callback: Callback<display.FoldStatus> = async (data: display.FoldStatus) => {
  try {
    let dis = DisplayUtils.getCurWindowDisplay(this.dialog?.subWindow);
    let windowRect = this.dialog?.extensionWindow.properties?.uiExtensionHostWindowProxyRect;
    if (this.waterFallMode || data === display.FoldStatus.FOLD_STATUS_EXPANDED ||
      (windowRect && windowRect.height > dis.height)) {
      this.updateContentCompoment();
    }
  } catch (err) {
    console.error(TAG, `Failed to touch foldStatusChange callback. code=${err?.code} msg=${err?.message}`);
  }
};
```

当两个前置条件均为 `false` 且 `windowRect` 有效时，表达式会继续求值 `dis.height`。如果显示查询返回 `undefined`，本次折叠布局更新会进入异常分支并被跳过。

## 影响

- 居中定位路径可能在已经切换子窗口布局模式后停止执行，导致通知授权对话框没有完成预期的尺寸或位置更新。
- 折叠状态变化时，本次布局更新可能被跳过，页面继续保留旧的窗口位置或尺寸。
- 两个位置都捕获了异常，当前证据不支持稳定进程崩溃、权限绕过、信息泄露或远程拒绝服务结论。

问题影响限于 PC 设备的通知授权对话框布局。是否能通过外部输入稳定制造显示查询失败尚未确认。

## 触发条件

居中定位位置需要同时满足：

1. PC 通知授权对话框进入 `updateContentCompoment`，第一次显示查询成功并判定需要移动到显示区域中心。
2. `moveToDisplayCenter` 在完成前置异步窗口操作后再次查询显示对象。
3. 第二次查询因显示 ID 缺失、子窗口状态变化或显示服务异常返回 `undefined`。
4. 代码继续读取 `display.width` 或 `display.height`。

折叠状态位置需要 PC 页面已注册 `foldStatusChange` 回调，前两个短路条件均不成立，`windowRect` 有效，同时显示查询返回 `undefined`。这些条件由源码可以确认，但未动态验证其稳定发生概率。

## 修复建议

建议在每次调用 `getCurWindowDisplay` 后立即检查返回值，并在缺失时记录明确错误后结束本次布局更新：

```typescript
let currentDisplay = DisplayUtils.getCurWindowDisplay(this.dialog?.subWindow);
if (currentDisplay === undefined) {
  console.error(TAG, 'current display is unavailable');
  return;
}
```

两个调用位置都应使用经过检查的局部变量。对于 `moveToDisplayCenter`，还可以由 `updateContentCompoment` 把首次验证过的 `Display` 作为参数传入，减少异步流程中的重复查询；若仍需重新查询，则必须再次验证。折叠状态回调也应在计算条件前完成检查，避免依赖短路求值掩盖缺失值。

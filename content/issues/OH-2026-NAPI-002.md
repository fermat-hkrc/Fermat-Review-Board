## 漏洞概述

`NativeModuleManager::LoadModuleLibrary()` 每次加载动态模块时先调用 `dlopen()` 或 `dlopen_ns()`，然后将返回的句柄交给 `EmplaceModuleLib()`。当 `moduleLibMap_` 已包含相同 `moduleKey` 时，`EmplaceModuleLib()` 返回原有句柄，但既不保存也不关闭本次新取得的句柄。

在 POSIX 动态链接器中，对已经加载的同一共享对象再次成功调用 `dlopen()` 通常会增加该对象的引用计数。丢失新句柄后，后续代码无法为这次加载调用配对的 `dlclose()`。即使 `UnloadNativeModule()` 最终关闭 map 中的标准句柄，重复加载增加的引用仍然存在，动态库及其依赖可能一直保留到进程结束。

该问题要求程序实际进入重复 `moduleKey` 的动态加载路径。源码提供了 `napi_load_module()` 和 `requireNapi()` 等模块加载入口，但正常的模块缓存会避免一部分重复磁盘加载；当前没有证据表明普通第三方能够绕过模块加载检查并任意加载系统动态库。因此，本条只确认重复加载路径上的资源泄漏，不声明直接的权限提升、远程拒绝服务或每次调用都会新增文件描述符。

仅确认当前 master commit `628b7d2a93f9acdcea7d3f125067bf84819a0790` 受影响。相关修复曾在 2026 年 7 月进入 master 历史，随后被明确回退；现有 tags 无法将该状态可靠映射到公开发布版本。


## 根本原因

**位置**: `module_manager/native_module_manager.cpp:1248`

`LoadModuleLibrary()` 在不同平台分支调用 `dlopen()` 或 `dlopen_ns()`。成功取得的 `lib` 最终直接传给 `EmplaceModuleLib()`：

```cpp
lib = dlopen(path, RTLD_LAZY);
// ...
lib = dlopen_ns(&ns, path, RTLD_LAZY);
// ...
return EmplaceModuleLib(moduleKey, lib);
```

**位置**: `module_manager/native_module_manager.cpp:186`

`EmplaceModuleLib()` 检测到重复 key 后丢弃 `lib`，只返回 map 中原有的标准句柄。当前源码注释明确说明新句柄会泄漏：

```cpp
auto it = moduleLibMap_.find(moduleKey);
if (it != moduleLibMap_.end()) {
    MODULEMNG_HILOG_WARN("module '%{public}s' already exists, discard duplicate handle", moduleKey.c_str());
    // Leak the new duplicate handle (original behavior). dlclose was reverted to avoid
    // refcount risk; the LIBHANDLE return still hands back the canonical tracked handle
    // so callers never observe a freed pointer.
    return it->second;
}
moduleLibMap_.emplace(moduleKey, lib);
return lib;
```

`moduleLibMap_` 只保留首次加载的句柄。调用方收到的也是该标准句柄，因此没有任何对象持有或负责释放重复加载取得的资源。

`UnloadNativeModule()` 只能从 map 取出并关闭标准句柄一次：

```cpp
handle = it->second;
moduleLibMap_.erase(it);
// ...
return UnloadModuleLibrary(handle);
```

这无法补偿未记录的额外 `dlopen()` 引用。

### 变更历史

提交 `3a126702` 曾在重复 key 分支调用 `UnloadModuleLibrary(lib)`，用于释放新句柄并保持原有 map 条目。提交 `71876f55` 随后删除了这次释放，理由是直接关闭传入句柄可能带来引用计数和调用方继续持有句柄的风险；回退说明同时明确接受重复句柄泄漏，并计划在独立修改中处理。当前版本保留回退后的逻辑。

这段变更历史与当前注释共同确认：重复加载取得的引用没有释放，且当前实现有意保留了这一行为。

## 影响

- 每次成功进入重复 key 分支都会留下一个无法通过 `moduleLibMap_` 回收的动态链接器引用。
- 后续卸载模块时，动态库及其依赖可能因剩余引用而无法卸载，相关映射、线程局部存储、构造资源或动态链接器元数据可能保留到进程退出。
- 如果调用方能够持续制造绕过正常模块缓存的重复加载，泄漏会累积，并可能增加进程内存或其他资源压力。

当前没有运行数据量化单次泄漏大小，也没有证明该路径会为每次加载保留新的文件描述符或新的完整代码映射。因此，影响限定为进程内动态库引用和关联资源无法按预期释放。

## 触发条件

1. 调用方具有使用 NAPI/Ark 运行时模块加载入口的正常执行能力，并请求一个通过模块加载检查的动态模块。
2. `LoadModuleLibrary()` 对该模块执行成功的 `dlopen()` 或 `dlopen_ns()`。
3. `moduleLibMap_` 中已经存在相同 `moduleKey`，但本次调用仍进入磁盘加载路径。例如，模块缓存状态与句柄 map 状态不一致，或者其他合法加载流程再次调用该底层路径。
4. `EmplaceModuleLib()` 返回原有句柄，丢失本次加载取得的引用。
5. 重复上述过程会累积未配对的动态链接器引用。

单纯在同一个引擎中重复请求已经正确缓存的模块，不一定触发本问题，因为上层缓存可能直接返回现有模块。是否存在可由普通应用稳定控制的缓存不一致路径尚未动态确认。

## 修复建议

为每次成功的 `dlopen()` 建立明确且唯一的所有权。`EmplaceModuleLib()` 是私有函数，当前生产代码只由 `LoadModuleLibrary()` 调用；可以明确约定传入的新句柄所有权转移给该函数。重复 key 时记录标准句柄，释放 map 锁后关闭新句柄，最后只向调用方返回仍由 map 管理的标准句柄。将 `dlclose()` 放在锁外，可以降低动态库析构函数重入模块管理器时发生死锁的风险。

```diff
+LIBHANDLE canonical = lib;
+bool duplicate = false;
+{
+    std::lock_guard<std::mutex> lock(moduleLibMutex_);
+    auto it = moduleLibMap_.find(moduleKey);
+    if (it == moduleLibMap_.end()) {
+        moduleLibMap_.emplace(moduleKey, lib);
+    } else {
+        canonical = it->second;
+        duplicate = true;
+    }
+}
+if (duplicate) {
+    UnloadModuleLibrary(lib);
+}
+return canonical;
```

生产修改还应检查 `UnloadModuleLibrary(lib)` 的返回值并记录关闭失败。若维护者不接受所有权转移约定，可让 `EmplaceModuleLib()` 返回 `{canonicalHandle, inserted}`，由 `LoadModuleLibrary()` 在 `inserted == false` 时关闭其局部的新句柄。两种实现都必须保证下游只收到标准句柄，不能继续持有已经关闭的重复句柄。

建议增加以下回归测试：

- 相同 `moduleKey` 的并发加载只执行一次实际 `dlopen()`。
- 重复 key 时，成功取得的每个非标准句柄都恰好执行一次 `dlclose()`。
- `EmplaceModuleLib()` 和 `LoadModuleLibrary()` 的返回值始终是 map 中仍然有效的标准句柄。
- 重复加载后执行 `UnloadNativeModule()`，动态链接器引用计数恢复到加载前状态。
- 模块缓存命中、模块注册失败和加载后初始化失败等邻近路径不会遗留 map 与实际引用不一致的状态。

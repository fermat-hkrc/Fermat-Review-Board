## 漏洞概述

`NapiDefineClass()` 在创建 JavaScript class 之前，先在堆上分配一个 `NapiFunctionInfo`。当属性数量超过栈内处理阈值时，`NapiCreateClassFunction()` 还会为属性 key 和 attribute 分别调用 `malloc()`。如果这两个数组中的任意一个分配失败，函数会释放已成功分配的临时数组并返回 `Undefined`，但不会释放此前创建的 `NapiFunctionInfo`。

正常路径会把 `NapiFunctionInfo` 交给 `NewConcurrentClassFunctionWithName()`，由注册的 `CommonDeleter` 在函数对象销毁时执行 `delete`。失败路径没有创建函数对象，也没有注册该 deleter，因此 `funcInfo` 的唯一指针在 `NapiDefineClass()` 返回后丢失。

该代码通过公开的 C 接口 `napi_define_class()` 到达，并作为 `ace_napi` 的生产源码进入组件 `base_group`。不过，该接口由 native addon 调用，`property_count` 不是普通 JavaScript 代码可直接控制的参数。触发还要求小型 `NapiFunctionInfo` 分配成功、随后较大的属性数组分配失败，因此严重程度定为 LOW。

仅确认当前 master commit `628b7d2a93f9acdcea7d3f125067bf84819a0790` 受影响。该失败分支由提交 `a7479f2d` 引入，当前 master 仍保留相同的所有权缺口；仓库现有 tags 均不包含该引入提交，因此不据此声明任何公开发布版本受影响。

## 根本原因

### `NapiFunctionInfo` 在调用 helper 前分配

**位置**: `native_engine/impl/ark/ark_native_engine.cpp:342`

```cpp
NapiFunctionInfo* funcInfo = NapiFunctionInfo::CreateNewInstance();
if (funcInfo == nullptr) {
    HILOG_ERROR("funcInfo is nullptr");
    return panda::JSValueRef::Undefined(vm);
}
funcInfo->callback = callback;
funcInfo->data = data;
funcInfo->env = env;
// ...
Local<panda::FunctionRef> fn =
    NapiCreateClassFunction(env, className, funcInfo, length, properties);
```

`CreateNewInstance()` 使用 `new(std::nothrow)` 创建对象：

```cpp
struct NapiFunctionInfo {
    static NapiFunctionInfo* CreateNewInstance()
    {
        return new(std::nothrow) NapiFunctionInfo();
    }
    // ...
};
```

此时 `funcInfo` 仍由 `NapiDefineClass()` 的局部变量独占，没有 RAII 对象负责异常或错误返回时的释放。

### 临时数组分配失败时没有释放 `funcInfo`

**位置**: `native_engine/impl/ark/ark_native_engine.cpp:308`

```cpp
Local<panda::JSValueRef> *keys =
    reinterpret_cast<Local<panda::JSValueRef> *>(
        malloc(sizeof(Local<panda::JSValueRef>) * propCount));
PropertyAttribute *attrs = reinterpret_cast<PropertyAttribute *>(
    malloc(sizeof(PropertyAttribute) * propCount));
if (attrs != nullptr && keys != nullptr) {
    size_t staticPropCount =
        NapiGetKeysAndAttrsFromProps(env, propCount, properties, keys, attrs);
    fn = panda::FunctionRef::NewConcurrentClassFunctionWithName(
        vm, context, ArkNativeFunctionCallBack, CommonDeleter,
        className.c_str(), reinterpret_cast<void*>(funcInfo), true,
        propCount, staticPropCount, keys, attrs);
} else {
    fn = panda::JSValueRef::Undefined(vm);
    napi_throw_error(env, nullptr, "malloc failed in napi_define_class");
}

if (keys != nullptr) {
    free(keys);
}
if (attrs != nullptr) {
    free(attrs);
}
return fn;
```

`keys` 和 `attrs` 都有配对的 `free()`。但是失败分支既没有调用 `NewConcurrentClassFunctionWithName()`，也没有执行 `delete funcInfo`。随后 `NapiDefineClass()` 处理 pending exception 并返回，原始指针没有其他保存位置。

### deleter 只覆盖成功的所有权转移

**位置**: `native_engine/impl/ark/ark_native_engine.cpp:1515`

```cpp
void CommonDeleter(void *env, void *externalPointer, void *data)
{
    auto info = reinterpret_cast<NapiFunctionInfo *>(data);
    if (info != nullptr) {
        delete info;
    }
}
```

`CommonDeleter` 能正确释放已经附加到函数对象的 `NapiFunctionInfo`。显式的 `malloc()` 失败分支没有函数对象承接该指针，因此不能依赖这个 deleter 完成清理。

### 入口和构建路径

**位置**: `native_engine/native_api.cpp:1693`

公开接口 `napi_define_class()` 将 `property_count` 和 `properties` 直接传入 `NapiDefineClass()`：

```cpp
auto resultValue = NapiDefineClass(
    env, newName, callback, data, nativeProperties, property_count);
```

`napi.gni` 将 `native_engine/native_api.cpp` 和 `native_engine/impl/ark/ark_native_engine.cpp` 同时列入 `napi_sources`。`ace_napi_static` 使用该列表，`ace_napi` 依赖该 source set，`napi_packages` 又作为组件的 `base_group` 构建。因此这不是仅测试或 sample 使用的代码。

## 影响

- 每次进入该分配失败分支，都会遗留一个无法再访问和释放的 `NapiFunctionInfo` 堆对象。
- 在失败后进程继续运行并重复调用该接口的构建或配置中，泄漏会逐次累积，并进一步增加已经存在的内存压力。
- 泄漏对象本身只保存 callback、data 和 env 等指针；当前证据不能证明它拥有这些指针指向的对象，因此本条不扩大为关联对象泄漏。
- 当前没有证据表明该问题可造成越界访问、敏感信息泄露、权限提升或由普通 JavaScript 代码直接触发。

## 触发条件

1. native addon 使用有效的 `napi_env`、constructor 和属性描述符数组调用 `napi_define_class()`。
2. `property_count` 超过 `panda::ObjectRef::MAX_PROPERTIES_ON_STACK`，使实现进入两个堆数组的分配分支。
3. `NapiFunctionInfo::CreateNewInstance()` 成功。
4. 随后的 `keys` 或 `attrs` 数组分配失败。
5. helper 返回前只释放临时数组，没有释放 `funcInfo`。若调用方在进程继续运行时重复满足上述条件，泄漏会累积。

普通 JavaScript 代码不能直接调用该 C API。能否通过某个具体 addon 的 JavaScript 接口间接控制属性数量或重复触发类定义，取决于该 addon 的实现，本条不作此类假设。

## 修复建议

在显式数组分配失败分支中，先释放所有已经取得的资源，再创建并抛出错误。清理应发生在 `napi_throw_error()` 之前，因为错误对象的创建在内存压力下也可能失败。

```diff
 if (attrs != nullptr && keys != nullptr) {
     // 构造函数对象，成功后由 CommonDeleter 管理 funcInfo
 } else {
+    free(keys);
+    free(attrs);
+    delete funcInfo;
     fn = panda::JSValueRef::Undefined(vm);
     napi_throw_error(env, nullptr, "malloc failed in napi_define_class");
+    return fn;
 }
```

更稳妥的实现是用 `std::unique_ptr<NapiFunctionInfo>` 保存初始所有权，并让 `NapiCreateClassFunction()` 明确报告函数对象是否已经接管该指针。只有在 `CommonDeleter` 成功注册后才调用 `release()`，这样新增错误分支也不会再次遗漏释放。

建议增加可注入 allocator 的回归测试，分别覆盖 `keys` 首次分配失败、`attrs` 在 `keys` 成功后分配失败以及两个数组均成功的路径。测试应验证失败路径恰好销毁一次 `NapiFunctionInfo`，成功路径仍仅由 `CommonDeleter` 销毁，并检查失败结果不会继续被当作有效函数对象使用。
